# Step 0-6. 링커·라이브러리와 실행 파일

## 1. 학습 목표

- 정적 라이브러리와 공유 라이브러리의 연결 방식 차이를 설명한다.

- 호스트 환경의 `main`과 GNU/Linux 실행 시작 코드의 역할을 구분한다.

## 3. 핵심 개념

### 링커는 무엇을 연결하는가?

**[GCC/Linux 구현]** 링커(linker)는 목적 파일과 필요한 라이브러리 입력을 읽어 심벌 참조를 정의와 연결하고, 출력의 코드/데이터 배치를 정하며, 가능한 재배치를 적용한다. 결과는 보통 실행 파일이지만 링커 옵션에 따라 공유 객체나 다른 재배치 가능 파일도 만들 수 있다. 단순히 여러 파일의 바이트를 순서대로 이어 붙이는 작업은 아니다.

**[C 표준]** 번역 단계에는 외부 참조를 해결하고 필요한 라이브러리 구성 요소를 연결하는 개념이 있다. 하지만 특정 링커 프로그램, ELF 파일, `.a` 또는 `.so` 확장자는 정하지 않는다. 실행 환경은 호스트 환경과 독립 환경(freestanding environment)으로 구분된다. 여기서는 표준 라이브러리와 `main`을 갖는 호스트 환경을 다룬다.

### 헤더는 사용 규약, 라이브러리는 구현

`#include <stdio.h>`를 통해 컴파일러는 `puts`의 선언 등 인터페이스를 알 수 있다. 일반적인 GNU/Linux 환경에서 `puts`의 실제 구현은 C 라이브러리(libc)가 제공한다. 헤더에 함수 정의가 들어가는 경우도 있지만, **표준 헤더 포함과 외부 라이브러리의 기계어 연결은 같은 작업이 아니다.**

**[GCC/Linux 구현]** 일반적인 `gcc hello.o -o hello`는 GCC 드라이버가 시작 코드와 기본 라이브러리 등을 링크 입력에 추가한다. 그래서 이 예제에서는 직접 `-lc`를 적지 않아도 된다. 반면 모든 외부 라이브러리가 자동 추가되는 것은 아니다. `ld hello.o -o hello`를 같은 뜻으로 사용하면 GCC가 마련하는 입력과 설정이 빠질 수 있다.

### 정적 라이브러리와 공유 라이브러리

**[GCC/Linux 구현: GNU/Linux 관찰]** 다음 비교는 GNU 계열 링크 환경의 일반적인 방식이다.

| 구분 | 정적 라이브러리(static library) | 공유 라이브러리(shared library) |
|---|---|---|
| 흔한 파일 | `libname.a` | `libname.so`, 버전이 붙은 `.so` |
| 형태 | 목적 파일들을 모은 아카이브 | 동적 연결에 쓰이는 공유 객체 |
| 일반적인 링크 시 처리 | 필요한 정의를 제공하는 멤버를 선택하여 출력에 포함 | 필요한 공유 객체와 동적 심벌 연결 정보를 출력에 기록 |
| 실행 시 요구 | 포함된 라이브러리 부분에는 원래 `.a`가 필요하지 않음 | 호환되는 공유 라이브러리를 로더가 찾을 수 있어야 함 |
| 변경의 영향 | 라이브러리 변경을 반영하려면 보통 다시 링크 | 호환성과 검색 경로가 맞아야 교체된 라이브러리를 이용할 수 있음 |

아카이브의 일부 멤버만 선택되는 것과 그 멤버 안의 불필요한 코드가 모두 제거되는 것은 다른 문제다. 정적 라이브러리 하나를 연결했다고 실행 파일 전체가 완전 정적 연결이 되는 것도 아니다. 예를 들어 사용자 `.a`의 코드는 포함하면서 libc는 공유 라이브러리를 사용할 수 있다.

공유 연결도 빌드 시 링커가 수행하는 작업이다. 일부 주소 확정과 재배치는 실행 시의 동적 링커/로더에 남길 수 있다. “공유 라이브러리는 링크할 때 전혀 검사하지 않는다”거나 “실행 파일에 관련 정보가 전혀 없다”는 설명은 틀리다.

## 4. 문법 또는 명령

먼저 목적 파일을 만든 뒤 링크한다.

```sh
gcc -std=c17 -Wall -Wextra -Wpedantic -O0 -c hello.c -o hello.o
gcc hello.o -o hello
./hello
echo $?
```

`echo $?`는 GNU/Linux 셸에서 바로 앞 명령의 종료 상태를 표시한다. 중간에 다른 명령을 실행하면 그 명령의 상태를 보게 된다. 출력이 정상인 환경에서 예제는 문자열 한 줄과 성공 종료 상태 `0`을 보여 준다.

**[GCC/Linux 구현: GNU Binutils/ELF GNU/Linux 관찰]** 링크 전후를 조사한다.

```sh
nm hello.o
readelf -h hello
readelf -l hello
readelf -d hello
gcc -### hello.o -o hello
```

- `readelf -h`: 파일 종류와 진입점 등을 확인한다. 비-PIE 실행 파일은 보통 `EXEC`, 위치 독립 실행 파일(PIE)은 `DYN`이다. `DYN`이라고 무조건 라이브러리는 아니다.
- `readelf -l`: 프로그램 헤더를 확인한다. `LOAD` 세그먼트나 동적 로더를 지정하는 `INTERP` 항목이 보일 수 있다.
- `readelf -d`: 동적 섹션을 확인한다. 동적 연결 예제에서는 `NEEDED`에 `libc.so.6` 같은 의존성이 보일 수 있다. 정적 연결 결과에는 동적 섹션이 없을 수 있다.
- `gcc -###`: 실행할 하위 명령을 보통 표준 오류로 표시하지만 실제 링크는 하지 않는다. 경로와 파일명은 시스템별로 다르다.

라이브러리 옵션은 다음 형태를 사용한다. 아래 명령은 작업 디렉터리에 `libgreet.a` 또는 적절한 `libgreet.so`가 준비된 경우의 형식 예시이며 기본 예제에서 바로 실행하는 명령은 아니다.

```sh
gcc main.o -L. -lgreet -o app
```

`-L.`는 현재 디렉터리를 링크 시 라이브러리 검색 경로에 더하고, `-lgreet`는 관례에 따라 `libgreet`라는 라이브러리를 찾는다. 일반적인 동적 링크 모드에서는 `.so`가 있으면 우선 선택할 수 있다. `.a`를 확실히 지정하려면 `gcc main.o ./libgreet.a -o app`처럼 파일 경로를 사용할 수 있다. `-L`는 실행 시 동적 로더의 검색 경로를 설정하지 않는다.

GNU `ld`의 일반적인 정적 아카이브 검색에서는 그 시점까지 생긴 미해결 참조에 따라 멤버를 꺼낸다. 따라서 `main.o`를 먼저 두고 이를 만족하는 라이브러리를 뒤에 두는 순서가 중요하다. 모든 링크 입력 순서가 무관하다고 외우지 않는다.

## 5. 최소 코드 예제

`hello.c`:

```c
#include <stdio.h>

int main(void)
{
    puts("link stage");
    return 0;
}
```

**[C 표준]** 호스트 환경의 이식 가능한 C17 예제다. GNU 확장이나 특정 CPU 코드 없이도 외부 표준 함수 구현을 연결하는 사례를 관찰할 수 있다. 정상적인 출력 환경을 가정하며 입출력 오류 처리는 이 Step의 주제가 아니다.

## 6. 코드 해석

| 줄 | 링크 및 실행과의 관계 |
|---|---|
| 1 | `puts`의 선언을 사용할 수 있게 한다. 링크 입력의 libc를 직접 선택하는 지시문이 아니다. |
| 2 | 빈 줄이다. 실행 동작을 추가하지 않는다. |
| 3 | 이 파일이 `main`의 정의를 제공한다. 표준의 호스트 환경에서 프로그램 시작 함수다. |
| 4 | 본문이 시작된다. |
| 5 | 외부 표준 함수 `puts`를 호출한다. 일반적인 GNU/Linux 환경에서는 libc가 구현을 제공한다. |
| 6 | `main`에서 0을 반환하여 성공 종료를 나타낸다. |
| 7 | 본문이 끝난다. |

`.o`에 있던 `U puts`는 링크에서 필요한 정의를 찾아 연결할 수 있다. 공유 연결 결과의 동적 심벌 표에는 여전히 미정의 형태의 `puts`가 보일 수 있다. 이것은 런타임에 지정된 공유 객체로 해결할 참조를 표현하므로 “링크 성공이면 모든 심벌이 파일 안에 정의된다”는 결론은 틀리다.

## 7. 내부 동작

### 빌드 시: 이름과 배치 연결

**[GCC/Linux 구현: ELF GNU/Linux 관찰]** 링커는 입력 섹션을 출력 섹션 등에 배치하고 심벌 정의를 찾으며 재배치 계산을 적용한다. 실행 파일의 **프로그램 헤더(program header)**는 로더가 메모리를 구성할 때 사용할 **세그먼트(segment)**를 설명한다. 앞 Step에서 본 섹션이 링크 관점의 분류라면, 세그먼트는 실행 시 적재 관점의 묶음이다. 한 세그먼트에 여러 섹션이 포함될 수 있다.

### 실행 시: 프로세스 준비와 시작 코드

**[C 표준]** 호스트 환경에서는 `main`을 통해 프로그램이 시작되며, 처음 호출된 `main`에서 반환하면 해당 값을 인수로 `exit`를 호출하는 것과 같은 효과가 있다. `main`보다 앞선 OS 진입 주소나 `_start`라는 심벌은 C 표준의 요구가 아니다. 독립 환경의 시작 방식은 구현 정의다.

**[GCC/Linux 구현: GNU/Linux 관찰]** `./hello`를 실행하면 셸이 OS에 프로그램 실행을 요청한다. 커널은 실행 파일의 정보를 바탕으로 주소 공간을 준비한다. 동적 연결 프로그램에 지정된 인터프리터가 있으면 동적 로더도 관여하여 공유 객체를 적재하고 필요한 재배치 등을 처리한다. 함수 심벌 연결의 일부는 설정에 따라 첫 호출까지 늦춰질 수도 있다.

그 뒤 실행 파일의 시작 코드가 C 실행 환경 초기화와 `main` 호출을 이어 준다. 흔히 시작 코드의 심벌 이름이 `_start`이며 glibc 환경에서는 `__libc_start_main` 같은 구성 요소가 관여한다. 동적 연결 프로그램에서 CPU가 가장 먼저 실행하는 사용자 코드가 반드시 실행 파일의 `_start`라는 뜻은 아니다. 동적 로더가 먼저 실행될 수 있다.

- **CPU 관점:** 준비된 메모리의 기계어를 실행하며 C의 함수 이름 자체를 해석하지 않는다.
- **메모리/OS 관점:** 실행 파일은 프로세스 자체가 아니라 프로세스 생성에 쓰이는 파일이다. 동적 로더, 메모리 매핑과 런타임 준비가 추가로 필요할 수 있다.
- **학습 경계:** 시작 코드의 역할까지만 이해한다. 레지스터별 호출 규약, PLT/GOT의 세부 구조와 직접 작성하는 시작 코드는 여기서 다루지 않는다.

## 8. 자주 하는 실수

- 헤더만 있으면 외부 라이브러리가 자동 연결된다고 생각하기: 선언과 구현 연결은 다르다.
- `gcc hello.o -c -o hello`로 실행 파일을 만들려고 하기: `-c`는 링크를 하지 않게 한다.
- GCC 대신 `ld`에 목적 파일 하나만 넘기기: 기본 시작 코드와 라이브러리 설정을 빠뜨릴 수 있다. 이 단계에서는 GCC 드라이버를 쓴다.
- `.a`를 연결하면 모든 라이브러리가 정적으로 연결됐다고 생각하기: 연결 방식은 구성 요소별로 섞일 수 있다.
- `-L.`만 있으면 실행 시 `.so`도 찾는다고 생각하기: 링크 시 검색과 실행 시 검색은 별개다.
- ELF의 `DYN`을 모두 실행 불가능한 라이브러리로 판단하기: PIE 실행 파일도 `DYN`일 수 있다.
- 링크 성공을 실행 성공으로 해석하기: 실행 시 필요한 공유 라이브러리가 없거나 프로그램 자체에 오류가 있을 수 있다.

## 9. 필수 실습

### 실습 A. 목적 파일에서 실행 파일로

- **목적:** 선언, 목적 파일의 외부 참조, 라이브러리 연결, 실행을 이어서 설명한다.
- **해야 할 일:** 최소 예제를 입력하고 `.o` 생성과 링크를 별도 명령으로 수행한다. 링크 전 `nm hello.o`를 읽고 실행 파일의 ELF 헤더와 동적 정보를 조사한다. `./hello`를 실행한 직후 종료 상태를 확인한다. `gcc -###` 출력에서 시작 코드와 기본 라이브러리 관련 입력을 찾아본다.
- **사용할 개념:** 링커, 심벌 해결, libc, 동적 의존성, 실행 파일, 시작 코드, 종료 상태
- **예상 관찰 결과:** 목적 파일 생성과 링크는 문자열을 실행 출력으로 내보내지 않는다. 실행 시 `link stage`와 줄바꿈이 출력되고 정상 환경에서는 종료 상태가 0이다. 일반적인 동적 연결 GNU/Linux에서는 libc 의존성을 관찰할 수 있다.
- **확인 포인트:** 환경이 정적 연결인지 동적 연결인지 도구 출력에 근거하여 기록한다. 파일 종류의 `DYN`만으로 결론 내리지 않는다. `puts`의 선언과 구현을 각각 어디에서 얻는지 설명한다.

## 10. 추가 실습

- **★ 기초:** `readelf -h hello.o`와 `readelf -h hello`를 비교하여 재배치 가능 파일과 실행 파일을 구별한다. `readelf -l hello`에서 메모리 적재 관점의 정보를 찾는다.
- **★★ 확장:** 직접 작성한 `greet.c`에 `void greet(void)`를 정의하고 그 안에서 `puts`를 호출한다. 별도 `main.c`에서 `void greet(void);`로 선언하여 호출한다. 각각 `.o`를 만들고 `ar rcs libgreet.a greet.o`로 정적 라이브러리를 만든 뒤 `gcc main.o ./libgreet.a -o app`으로 연결한다. 사용자 라이브러리를 포함해도 libc가 동적 의존성으로 남는지 관찰한다. 이 연습은 작은 인터페이스를 따라 쓰는 선택 실습이며 함수 설계 전반을 다루지 않는다.

전체 정적 연결을 위한 `-static`이나 직접 만드는 `.so`는 필수 실습이 아니다. 정적 시스템 라이브러리의 설치 여부와 런타임 검색 설정 같은 별도 환경 문제를 이 Step의 성공 조건으로 삼지 않는다.

## 11. 확인 문제

1. 헤더 포함과 라이브러리 연결은 어떻게 다른가?
2. `gcc hello.o -o hello`에서 `-lc`를 생략해도 보통 `puts`를 사용할 수 있는 이유는 무엇인가?
3. 정적 라이브러리와 공유 라이브러리는 일반적으로 출력에 무엇을 남기는가?
4. 정적 아카이브보다 이를 참조하는 목적 파일을 앞에 두는 이유는 무엇인가?
5. 성공적으로 링크된 동적 실행 파일에 미정의 동적 심벌이 남을 수 있는가?
6. C 표준의 `main`과 GNU/Linux의 `_start`는 같은 개념인가?

<details>
<summary>정답과 해설 펼치기</summary>

1. 헤더는 컴파일에 필요한 선언 등을 제공한다. 라이브러리 연결은 구현의 정의를 참조와 연결하는 작업이다.
2. GCC 드라이버가 일반적인 호스트 환경 링크에 기본 C 라이브러리와 시작 코드 등을 추가하기 때문이다. C 표준이 `gcc` 명령을 정한 것은 아니다.
3. 정적 아카이브는 필요한 멤버의 코드/데이터 등을 출력에 포함시킨다. 공유 연결은 필요한 공유 객체와 런타임 연결 정보를 남기며 라이브러리 구현 전체를 복사하지 않는다.
4. GNU `ld`의 일반적인 아카이브 검색에서는 그 시점까지의 미해결 참조를 만족시키는 멤버를 선택하므로 참조가 먼저 제시되어야 한다.
5. 가능하다. 런타임 공유 객체가 제공할 심벌을 동적 링커가 해결하도록 남길 수 있다.
6. 아니다. `main`은 C 호스트 환경의 시작 함수이고 `_start`는 흔한 구현의 시작 코드 심벌이다. OS와 동적 로더가 `main`보다 앞서 준비 작업을 할 수 있다.

</details>

## 12. 핵심 정리

- 링커는 심벌을 연결하고 배치를 정하며 재배치를 처리한다.
- 헤더의 선언을 아는 것과 라이브러리의 구현을 연결하는 것은 다르다.
- 정적 라이브러리의 일부 포함과 실행 파일 전체의 정적 연결은 다르다.
- 공유 연결에서는 실행 시에도 의존성 탐색과 주소 연결이 필요할 수 있다.
- **[C 표준]**의 `main` 시작 규칙과 **[GCC/Linux 구현]**의 로더/시작 코드 절차를 구분한다.
