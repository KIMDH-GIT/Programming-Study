# Step 0-8. 단계별 오류 구분

## 1. 학습 목표

- 전처리 진단, C 문법·제약 조건 진단, 어셈블러 오류, 링커 오류를 구별한다.
- 정의되지 않은 심볼과 중복 정의된 심볼의 차이를 설명한다.
- 로딩 실패, 실행 중 실패, 논리 오류를 빌드 실패와 분리한다.
- 가장 먼저 발생한 실패의 명령과 진단을 근거로 수정 대상을 좁힌다.

## 2. 선수 지식

[Step 0-7](0-7-build-and-run.md)의 정상 빌드·실행을 먼저 완료한다. `.i`, `.s`, `.o`와 실행 파일의 역할, 선언과 정의가 다르다는 점을 알고 있으면 된다. 이 Step은 오류를 분류하며 새 문법 전체를 학습하지 않는다.

**[GCC/Linux 구현]** GCC, GNU 어셈블러·링커를 사용하는 Linux 환경을 가정한다. 실제 GCC는 다른 링커를 사용할 수도 있으므로 진단 문자열이나 출력 프로그램 이름을 절대적인 규칙으로 외우지 않는다.

## 3. 핵심 개념

**진단(diagnostic)**은 구현이 번역상의 문제를 알리는 메시지다. **[C 표준]** 전처리 번역 단위 또는 번역 단위에 문법 규칙이나 제약 조건 위반이 있으면 적어도 하나의 진단이 요구된다. 표준은 모든 위반을 하나씩 찾아내거나 반드시 번역을 거부하라고 일반적으로 요구하지 않는다. 따라서 "경고이면 표준에 맞는 코드"라는 결론은 잘못이다. 반대로 진단이 없다고 정의되지 않은 동작이나 논리 오류까지 배제되지는 않는다.

**[GCC/Linux 구현]** `warning`과 `error`의 분류, 종료 상태, 진단 서식은 도구의 정책이다. `-Werror`는 경고를 오류로 취급하는 GCC 정책을 추가할 뿐 C 언어의 의미를 바꾸지 않는다. 여러 진단은 첫 문제로부터 연쇄 발생할 수 있다. 먼저 실패한 명령과 첫 관련 진단을 확인하되, 수정 후 전체 진단도 다시 읽는다.

| 분류 | 원인과 대표 관찰 | 우선 확인할 입력 |
|---|---|---|
| 전처리 진단 | 없는 헤더 포함, `#error` 지시문; 보통 `-E`부터 실패 | `#include`, 헤더 검색 경로, 전처리 조건 |
| C 문법·제약 조건 진단 | 세미콜론 누락, 선언되지 않은 식별자 사용; `-E`는 통과해도 `-S`에서 진단 가능 | 원본 소스의 행과 선언 |
| 어셈블러 오류 | 알 수 없는 명령이나 잘못된 지시문; `.s`를 `.o`로 바꾸지 못함 | 어셈블리 입력, 대상 아키텍처 |
| 링커: 정의 누락 | 필요한 외부 정의를 찾지 못함; 흔히 `undefined reference` | 누락된 오브젝트·라이브러리, 이름 |
| 링커: 중복 정의 | 동일한 외부 함수의 정의를 두 번 제공; 흔히 `multiple definition` | 중복 입력과 중복 함수 정의 |
| 실행 요청·로딩 실패 | 경로·권한·실행 형식 또는 동적 라이브러리 문제 | 실행 경로, 환경, 실행 파일 형식 |
| 실행 중 실패 | 시작 뒤 비정상 종료, 입출력 실패 등 | 실행 입력, 환경, 프로그램 동작 |
| 논리 오류 | 정상 종료했지만 요구한 출력과 다름 | 기대 결과와 실제 결과의 비교 |

표의 명령별 경계와 메시지는 **[GCC/Linux 구현]** 관찰이다. 실제 구현에서는 전처리와 C 컴파일이 같은 내부 프로그램에서 처리될 수 있다. `.c`를 직접 `gcc -c`에 넣었을 때 실패했다고 곧바로 "어셈블러 오류"인 것은 아니다. 그 호출은 전처리와 C 컴파일도 수행한다.

## 4. 문법 또는 명령

아래는 **[GCC/Linux 구현]**의 단계 격리 절차다. 정상 예제를 `hello.c`로 저장하고 한 줄씩 실행한다. 실패한 줄 뒤의 단계는 진행하지 않는다. 매번 다른 명령 전에 `printf 'status=%s\n' "$?"`를 실행하여 상태를 기록한다.

```sh
gcc -std=c17 -E hello.c -o hello.i
gcc -std=c17 -Wall -Wextra -pedantic -S hello.i -o hello.s
gcc -c hello.s -o hello.o
gcc hello.o -o hello
./hello
```

의도적인 결함 실험은 정상 파일을 보존하고 **매번 정상본에서 만든 새 복사본**에 한 가지 변경만 적용한다. 아래 조각은 서로 합쳐 쓰는 프로그램이 아니라 원인별 실험 재료다.

| 실험 | 변경 또는 입력 | 검사 명령 |
|---|---|---|
| 전처리 | `preprocess.c` 맨 위에 `#error intentional preprocessing failure` 추가 | `gcc -E preprocess.c -o preprocess.i` |
| 문법 | `syntax.c`의 `puts` 호출 끝 세미콜론 삭제 | `gcc -std=c17 -S syntax.c -o syntax.s` |
| 제약 조건 | `constraint.c`의 `return 0;`를 `return unknown_value;`로 바꾸고 이 이름은 선언하지 않음 | `gcc -std=c17 -pedantic-errors -S constraint.c -o constraint.s` |
| 어셈블러 | `bad.s`에 GNU as 지시문 `.error "intentional assembler failure"` 한 줄 작성 | `gcc -c bad.s -o bad.o` |
| 정의 누락 | `missing.c`에서 `main` 위에 `int missing(void);` 선언을 추가하고 `return 0;`를 `return missing();`으로 변경. 정의는 제공하지 않음 | `gcc -std=c17 -c missing.c -o missing.o` 성공 확인 뒤 `gcc missing.o -o missing` |
| 중복 정의 | 정상본으로 만든 동일 `hello.o`를 명시적으로 두 번 입력 | `gcc hello.o hello.o -o duplicate` |

`#error`는 **[C 표준]** 지시문이며 진단을 요구한다. 위 `.error`는 **[GCC/Linux 구현]**에서 GNU 어셈블러가 제공하는 지시문이지 C 문법이 아니다. 이 방식은 특정 CPU의 잘못된 명령 이름을 추측하는 것보다 재현 가능하다. 어셈블러 오류를 유도하려고 정상 GCC 출력의 임의 바이트를 손상시키지 않는다.

## 5. 최소 코드 예제

결함 실험의 기준이 되는 정상 `hello.c`다. **[C 표준]** 호스트 환경에서 이식 가능한 코드다.

```c
#include <stdio.h>
int main(void)
{
    puts("Build baseline");
    return 0;
}
```

정상 표준 출력 환경에서 `Build baseline` 한 줄을 기대한다. 정상본의 빌드와 실행을 먼저 확인해야 이후 실패가 실험에서 생긴 것인지 판단할 수 있다.

## 6. 코드 해석

| 줄 | 해석 및 결함 실험과의 관계 |
|---|---|
| 1 | `puts` 선언을 제공받는다. 헤더 탐색 실패는 C 문장 검사 이전의 문제다. |
| 2 | `main`의 외부 함수 정의다. 이 정의가 든 오브젝트를 두 번 넣으면 중복 정의 실험이 된다. |
| 3 | 본문의 시작이다. |
| 4 | 함수 호출 식에 세미콜론을 붙인 문장이다. 세미콜론 삭제는 문법 진단 대상이다. |
| 5 | 성공 종료를 요청한다. 선언만 있는 `missing` 호출로 바꾸면 외부 정의에 대한 참조를 만들 수 있다. |
| 6 | 본문의 끝이다. |

**[C 표준]** 선언은 이름과 타입 등의 정보를 제공하고 정의는 실제 함수 본문을 제공한다. 호출 전에 선언이 있어 C 컴파일을 통과해도 전체 프로그램에 필요한 정의가 없을 수 있다. 이런 프로그램 간 요구 사항의 모든 위반에 반드시 C 번역 진단이 요구되는 것은 아니다. 여기서는 실제 링커 진단으로 관찰한다.

## 7. 내부 동작

**[GCC/Linux 구현] 전처리·컴파일:** 헤더와 매크로를 처리한 뒤 토큰·문법·타입 등의 검사가 이어진다. 진단 위치는 전처리 결과의 줄 정보로 원본 소스를 가리킬 수 있다. 세미콜론 누락 때문에 그 다음 `return` 근처를 가리키더라도 그 줄만 고집하지 않는다.

**[GCC/Linux 구현] 어셈블·링크:** 어셈블러는 기계 명령과 데이터, 심볼·재배치 정보가 든 재배치 가능한 오브젝트를 만든다. 다른 파일에서 정의될 외부 심볼은 미해결 참조로 남을 수 있다. 링커는 입력 전체를 대상으로 참조를 연결하므로 오브젝트 생성 성공과 링크 성공은 다르다. 동일한 외부 `main` 정의를 두 번 명시적으로 입력하는 실험은 일반적인 중복 정의 오류를 재현한다. 모든 종류의 동명 심볼이 항상 오류인 것은 아니며 약한 심볼 등의 구현 확장은 이 Step 범위 밖이다.

**[GCC/Linux 구현] 로딩·실행:** 실행 경로를 셸이 찾지 못하거나 권한이 없으면 프로그램 본문에 도달하지 않는다. ELF 인터프리터가 없거나 필요한 공유 라이브러리를 동적 로더가 찾지 못해도 시작이 실패할 수 있다. 동적 심볼 해소는 지연될 수 있어 모든 로더 관련 실패가 반드시 `main` 전에 일어나는 것은 아니다. 실제 실행 파일이 있는데도 인터프리터 문제로 "없음" 계열 메시지가 나올 수 있으므로 파일 이름만 추측해서 고치지 않는다.

**[C 표준]와 실행 실패:** 정의되지 않은 동작은 충돌, 특정 신호, 특정 종료 상태를 보장하지 않는다. 따라서 잘못된 포인터 접근을 "반드시 segmentation fault가 나는 실험"으로 만들지 않는다. 안전하게 실행 결과를 분리해서 보려면 정상 프로그램의 반환값이나 출력 문자열을 바꾼다. `return 1;`은 유효한 C 코드지만, 값 1의 실패 상태 해석은 이 실습의 **[GCC/Linux 구현]** 관찰이다. C에서 이식 가능한 실패 종료 값은 `<stdlib.h>`의 `EXIT_FAILURE`다.

## 8. 자주 하는 실수

- 모든 GCC 메시지를 "컴파일 오류"라고만 기록한다. 전체 빌드라는 넓은 표현과 C 컴파일 단계라는 좁은 표현을 구별한다.
- `undefined reference`를 헤더가 없다는 뜻으로 해석한다. 헤더의 선언이 있어도 링크 입력에 정의가 없을 수 있다.
- 경고를 없애려고 옵션만 끈다. 먼저 실제 원인을 확인하며 진단 억제를 수정으로 취급하지 않는다.
- 하나의 파일에 여러 결함을 넣어 실험한다. 앞 단계 실패가 뒤 결함을 가려 분류가 불가능해진다.
- `-c` 성공을 실행 가능성의 증거로 삼는다. 외부 정의는 링크 때 필요할 수 있다.
- 실패한 빌드 뒤 오래된 실행 파일을 실행한다. 정상본과 결함본의 이름을 분리한다.
- Linux의 비정상 종료 상태 숫자 하나로 원인을 단정한다. 종료 상태는 단서이며 명령, 진단, 발생 시점도 필요하다.

## 9. 필수 실습

### 여섯 가지 빌드 결함의 최초 실패 지점 찾기

- **목적:** 오류 메시지 암기가 아니라 입력·단계·증거로 실패를 분류한다.
- **해야 할 일:** 정상본을 빌드·실행한 뒤 4절의 전처리, 문법, 제약 조건, 어셈블러, 정의 누락, 중복 정의 실험을 각각 수행한다. 실험마다 변경 내용, 명령, 첫 관련 진단, 직후 종료 상태, 마지막 성공 단계를 기록한다. 정의 누락 실험에서는 오브젝트 생성 성공과 링크 실패를 둘 다 기록한다. 마지막에는 결함 복사본 하나만 원상복구하여 성공을 확인한다.
- **사용할 개념:** 전처리, 문법 규칙, 제약 조건, 외부 선언·정의, 심볼, 단계 중단 옵션.
- **예상 관찰 결과:** 각 의도적 결함에 대응하는 도구 단계가 진단과 비성공 상태를 남긴다. 정의 누락은 `-c`를 통과하지만 링크에서 드러난다. 진단 문구·경로·행 번호는 환경마다 달라질 수 있다. 이는 **[GCC/Linux 구현]** 관찰이다.
- **확인 포인트:** 뒤 단계가 실제로 실행되었는가? 실패한 파일의 존재만으로 성공이라고 판단하지 않았는가? 원인 수정 뒤 같은 검사 명령이 성공했는가?

명령 및 빈 기록표: [실습 README](../../exercises/00-compilation/0-8/README.md).

## 10. 추가 실습

- ★ **논리 오류와 실패 상태:** 정상본의 새 복사본에서 출력만 기대와 다르게 바꾼다. 또 다른 복사본에서는 반환값만 1로 바꾼다. 각각 빌드 상태, 출력, 실행 상태를 따로 비교한다. 비성공 상태 자체가 충돌의 증거는 아니다.
- ★★ **실행 요청 실패:** 별도 복사한 실행 파일에만 `chmod a-x`를 적용해 실행을 시도하고 진단을 기록한다. 이후 `chmod u+x`로 복원한다. 이는 Linux 권한 실험이며 동적 로더 오류 실험이 아니다. 시스템 라이브러리나 로더는 변경하지 않는다.

## 11. 확인 문제

1. `gcc -c sample.c`가 실패했으면 어셈블러 오류라고 단정할 수 있는가?
2. 전처리 성공 뒤 세미콜론 누락이 드러날 수 있는 이유는 무엇인가?
3. `int missing(void);`가 있어도 링크에서 정의를 찾지 못하는 이유는 무엇인가?
4. `undefined reference`와 `multiple definition`은 무엇이 반대인가?
5. 출력이 틀렸지만 상태 0으로 끝난 경우 어느 범주인가?
6. C 표준은 정의되지 않은 동작이 항상 충돌하도록 요구하는가?

<details>
<summary>정답과 해설</summary>

1. 아니다. `.c` 입력이면 전처리와 C 컴파일도 거친다. 진단이나 단계 분리 결과가 필요하다.
2. 전처리는 일반 C 문장 전체의 문법 검사를 완료하는 단계가 아니다.
3. 선언은 함수 본문을 제공하지 않는다. 정의가 든 링크 입력이 별도로 필요하다.
4. 전자는 필요한 정의가 없고, 후자는 허용되지 않는 복수의 정의가 제공된 경우다.
5. 명세와 결과가 다르므로 논리 오류다. 종료 상태 0은 정확성 증명이 아니다.
6. 아니다. 동작에 대한 요구가 없으므로 특정 충돌이나 진단을 보장할 수 없다.

</details>

## 12. 핵심 정리

실패한 명령과 가장 이른 관련 진단을 보존하고, 한 번에 한 원인만 바꾼다. 선언의 유효성, 외부 정의 연결, 실행 가능성, 결과의 정확성은 서로 다른 검사다. 셸·ELF·로더·종료 상태 메시지는 Linux 구현 관찰로 기록한다.
