# Step 0-3. 전처리기와 `.i` 파일: `gcc -E`

기준: C17의 호스트 환경과 GCC/Linux 명령. 전처리를 "문자열을 아무렇게나 바꾸는 작업"이 아니라 전처리 토큰과 지시문을 처리하는 과정으로 이해한다.

## 1. 학습 목표

- `#include`, 객체형 `#define`, 조건부 포함의 역할을 구별한다.
- `gcc -E`로 `.i` 파일을 생성하고 원본과 의미 있는 차이를 찾는다.
- 주석 처리, 매크로 확장, 문자열 내부 비치환을 토큰 관점으로 설명한다.
- GCC 줄 표시자(line marker)와 C 표준 전처리 의미를 구분한다.

## 2. 선수 지식

- [Step 0-1](0-1-compilation-overview.md)의 전체 번역 흐름.
- [Step 0-2](0-2-c-source-and-header.md)의 헤더 포함과 번역 단위.
- `puts`가 문자열과 줄바꿈을 출력하며 `main`의 `return 0`이 성공 종료임을 읽을 수 있으면 된다.

## 3. 핵심 개념

### 전처리는 무엇을 바꾸는가?

**[C 표준]** 전처리 지시문(preprocessing directive)은 전처리 과정에서 처리하는 명령이다. 줄의 첫 전처리 토큰으로 나타나는 `#` 뒤에 지시문 이름이 온다. 앞에 공백이 있어도 된다. 지시문은 보통 줄바꿈으로 끝나며 C 문장의 세미콜론으로 끝내지 않는다.

| 기능 | 대표 형태 | 전처리 결과 |
|---|---|---|
| 소스 파일 포함 | `#include "message.h"` | 지정한 내용이 포함되고 그 안의 지시문도 처리된다. |
| 객체형 매크로 정의 | `#define MESSAGE "ready"` | 이후 `MESSAGE` 전처리 토큰을 치환할 규칙이 생긴다. |
| 조건부 포함 | `#if defined(VERBOSE)` | 조건에 맞는 그룹을 남기고 다른 그룹은 제외한다. |

매크로는 C 변수가 아니다. 타입이나 런타임 저장 공간을 갖지 않으며, 정의 지점 이후의 토큰 처리에 영향을 준다. 치환 결과는 추가 매크로 확장 여부를 다시 검사한다. 전처리는 토큰 단위이므로 식별자 일부나 문자열 리터럴 안의 글자를 임의로 치환하지 않는다. `MESSAGE`는 확장되지만 `"MESSAGE"`는 그대로 문자열이고 `MESSAGE_COUNT`는 다른 식별자다.

### 조건부 포함은 실행 중 분기가 아니다

`#if`·`#ifdef`는 빌드할 때 어떤 토큰을 뒤 단계에 전달할지 정한다. 런타임 변수나 사용자 입력을 읽어 결정하는 C의 `if` 문과 다르다. `#if defined(VERBOSE)`는 매크로가 **정의되어 있는가**만 묻는다. 값이 0으로 정의되어 있어도 참이다. 숫자 값을 검사하려면 `#if VERBOSE`처럼 다른 조건을 써야 한다.

### `.i` 파일은 무엇인가?

**[GCC/Linux 구현]** `gcc -E`는 전처리에서 멈추며 기본적으로 표준 출력에 텍스트를 쓴다. `-o main.i`로 저장한 `.i`는 GCC가 전처리된 C 입력으로 인식하는 파일이다. `.i`는 실행 파일도 어셈블리도 아니다. 포함한 시스템 헤더 때문에 원본보다 훨씬 길 수 있다.

**[C 표준]** `.i`라는 파일 형식이나 확장자를 요구하지 않는다. GCC의 출력에는 위치 추적용 줄 표시자와 구현별 선언·확장 표기가 보일 수 있다. 내 소스가 이식 가능한 C17이라는 사실이 모든 시스템 헤더와 전처리 출력도 모든 컴파일러에서 그대로 재사용 가능하다는 뜻은 아니다.

## 4. 문법 또는 명령

`main.c`가 있는 디렉터리에서 실행한다.

```sh
gcc -std=c17 -Wall -Wextra -pedantic -E main.c -o main.i
less main.i
gcc -std=c17 -E -P main.c -o main-plain.i
gcc -std=c17 -Wall -Wextra -pedantic main.i -o main && ./main
```

- `less`에서는 `/int main`으로 검색하고 `q`로 나온다. `less`는 Linux의 텍스트 열람 도구이며 C 표준 기능이 아니다.
- `-P`는 GCC 전처리 출력의 줄 표시자를 억제한다. 기본 출력과 비교하는 관찰용이며 오류 위치 추적 정보가 줄어든다.
- GCC는 `.i` 입력에 전처리를 다시 수행하지 않고 이후 번역·링크를 진행한다. 원본 매크로를 바꾸려면 원본을 다시 전처리해야 한다.
- `-E` 성공은 전체 C 문법·타입 검사나 링크 성공을 보장하지 않는다.

명령줄에서 객체형 매크로를 정의하는 GCC 옵션도 있다.

```sh
gcc -std=c17 -DVERBOSE=1 -E main.c -o main-verbose.i
```

**[GCC/Linux 구현]** `-D이름=치환목록`은 소스 처리 전에 매크로를 정의한다. 소스의 `#define`은 **[C 표준]** 기능이지만 이 명령줄 옵션 자체는 표준이 아니다. 소스에서도 같은 이름을 다른 내용으로 재정의하는 상황은 피한다.

## 5. 최소 코드 예제

관찰용 `main.c`:

```c
#include <stdio.h>
#define MESSAGE "preprocessing"

int main(void)
{
    /* MESSAGE inside this comment is not output. */
    puts(MESSAGE);
    puts("MESSAGE");
    return 0;
}
```

정상적인 출력 환경에서 결과는 두 줄이다.

```text
preprocessing
MESSAGE
```

이 예제는 객체형 매크로의 기본 확장을 보여 준다. 조건부 포함을 추가하는 필수 실습의 완성 코드는 제공하지 않는다.

## 6. 코드 해석

| 줄 | 전처리와 이후 동작 |
|---|---|
| 1 | 표준 헤더를 포함한다. `.i`에서 `puts` 관련 선언을 찾을 수 있지만 주변 내용과 형태는 구현에 따라 다르다. |
| 2 | 치환 규칙을 정의한다. 기본 `-E` 출력에서는 이 `#define` 지시문 자체가 남지 않는다. |
| 3 | 가독성을 위한 빈 줄이며 출력의 빈 줄 배치는 GCC의 출력 방식에 좌우된다. |
| 4~5 | 일반 C 토큰인 함수 머리와 여는 중괄호는 이후 컴파일 단계에 전달된다. |
| 6 | 주석은 표준의 추상적 3단계에서 공백 하나로 대체된다. 주석 속 이름을 매크로로 출력하지 않는다. |
| 7 | `MESSAGE`가 문자열 리터럴 `"preprocessing"`으로 확장된다. `puts` 호출 자체를 실행하는 것은 아니다. |
| 8 | `"MESSAGE"`는 하나의 문자열 리터럴 토큰이므로 내부 글자는 확장되지 않는다. |
| 9~10 | 일반 C의 반환문과 닫는 중괄호다. 실행될 때 성공 종료를 알린다. |

## 7. 내부 동작

### 토큰과 주석

**[C 표준]** 소스를 전처리 토큰으로 나누고 주석을 공백으로 바꾸는 것은 추상적 번역 3단계, 지시문 처리와 매크로 확장은 4단계다. 따라서 `int/**/value;`는 토큰을 붙여 `intvalue;`로 만들지 않는다. `int value;`처럼 두 토큰의 경계가 유지된다. GCC의 출력이 원본 공백 개수와 정확히 같을 필요는 없다.

역슬래시와 바로 다음 줄바꿈의 연결은 그보다 앞선 2단계다. 따라서 `//` 주석의 마지막에 역슬래시를 놓으면 다음 물리적 줄까지 주석이 이어지는 뜻밖의 결과를 만들 수 있다. 이 Step의 실습에서는 줄 연결을 사용하지 않는다.

### 줄 표시자와 실제 위치

**[GCC/Linux 구현]** `.i`에는 `# 1 "main.c"`와 비슷한 줄이 나타난다. 뒤에 추가 숫자 플래그가 붙을 수도 있다. 이는 다음 출력 부분의 원래 파일·행과 파일 진입·복귀 같은 정보를 표시하여 후속 진단이 원본 위치를 가리키도록 돕는다. `#include`가 처리되지 않고 남은 것이 아니다. 표준 `#line` 지시문과 목적은 관련 있지만 이 GCC 출력 문법 자체를 ISO C의 소스 문법으로 일반화하면 안 된다.

**[C 표준]** 전처리는 실행 중 메모리 할당이나 CPU 명령 실행과 별개의 번역 작업이다. 조건부 포함에서 제외된 코드는 뒤 컴파일 단계에 전달되지 않는다. 다만 앞선 문자 처리·토큰화와 조건부 지시문의 올바른 짝은 여전히 중요하다. `#if 0` 안에 닫히지 않은 주석 등을 넣어도 안전하다고 생각하면 안 된다.

## 8. 자주 하는 실수

- **`.i`를 원본 대신 직접 수정한다.** 다시 전처리하면 덮어써진다. 원본을 고쳐 새 결과를 생성한다.
- **`gcc -E` 뒤 프로그램 출력이 없다고 오류라고 생각한다.** 실행은 아직 하지 않았다.
- **`#define MESSAGE "ready";`처럼 세미콜론을 붙인다.** 세미콜론도 치환 목록에 들어가 사용 위치의 문법을 망가뜨릴 수 있다.
- **매크로가 문자열 속 이름도 치환한다고 생각한다.** 토큰의 종류와 경계를 구별한다.
- **`-DVERBOSE=0`이면 `defined(VERBOSE)`가 거짓이라고 생각한다.** 정의 여부와 숫자 값 검사는 다르다.
- **줄 표시자를 전처리 오류로 오해한다.** 원본 위치 추적 정보이며 `-P`로 억제할 수 있다.
- **전처리 성공을 완전한 빌드 성공으로 여긴다.** 뒤 단계에서 문법·타입·연결 오류가 드러날 수 있다.

## 9. 필수 실습

### 실습 A. 토큰 치환과 조건부 포함 비교

- **목적:** 매크로가 확장되는 위치와 빌드 시 선택되는 코드를 직접 확인한다.
- **해야 할 일:** [실습 안내](../../exercises/00-compilation/0-3/README.md)에 따라 최소 예제를 직접 입력한다. `#if defined(VERBOSE)`·`#else`·`#endif`를 사용하여 `verbose` 또는 `quiet`를 출력하는 호출 하나를 선택하도록 확장한다. 기본, `-DVERBOSE=1`, `-DVERBOSE=0`의 `.i`를 만들고 자신의 `main` 부분을 비교한 뒤 각각 빌드·실행한다.
- **사용할 개념:** 객체형 매크로, 문자열 리터럴 토큰, 주석, 조건부 포함, `gcc -E`, `-D`, `.i` 입력.
- **예상 관찰 결과:** `MESSAGE`의 일반 토큰 사용은 치환되지만 문자열 내부는 유지된다. 기본 상태와 매크로가 정의된 상태는 선택한 호출이 다르다. `=1`과 `=0`은 둘 다 정의된 상태이므로 `defined` 조건에서 같은 그룹을 선택한다.
- **확인 포인트:** 비교 대상을 구현별 시스템 헤더 전체가 아닌 자신의 함수 부분으로 좁혔는가? 제외된 호출이 `.i`에서 사라졌는가? 원본 수정 뒤 `.i`를 다시 생성했는가? 전처리 결과를 실행 결과와 구별했는가?

## 10. 추가 실습

- ★ **위치 정보:** `-P` 유무로 생성한 두 출력을 비교한다. 줄 표시자 유무와 자신의 함수 내용이라는 두 관찰 대상을 분리한다.
- ★★ **헤더도 입력:** 작은 프로젝트 헤더에 출력용 매크로를 옮긴다. 헤더 값을 수정한 뒤 기존 `.i`를 빌드한 결과와 다시 전처리한 `.i`를 빌드한 결과를 비교한다. 기존 `.i`는 당시의 전처리 결과를 담은 파일임을 설명한다.

## 11. 확인 문제

1. `gcc -E main.c`에서 `-o`가 없으면 보통 결과가 어디로 가는가?
2. `MESSAGE`는 확장되는데 `"MESSAGE"`는 확장되지 않는 이유는?
3. `int/**/value;`에서 주석을 처리하면 `intvalue;`가 되는가?
4. `-DVERBOSE=0`을 줬을 때 `#if defined(VERBOSE)`는 참인가?
5. `.i`에 보이는 `# 1 "main.c"`와 같은 줄은 무엇인가?
6. 전처리가 성공하면 함수 정의 누락에 의한 링크 오류도 없다고 말할 수 있는가?

1. 표준 출력으로 간다. 터미널에서 직접 실행하면 긴 텍스트가 화면에 보일 수 있다.
2. 전자는 치환 대상 식별자 토큰이고, 후자는 문자열 리터럴 하나다. 전처리기는 문자열 내부 글자를 매크로 이름으로 다시 나누지 않는다.
3. 아니다. 주석은 공백 하나로 대체되므로 `int`와 `value`의 토큰 경계가 유지된다.
4. 참이다. 0이라는 치환 목록과 관계없이 이름이 정의되어 있다. 숫자 값 조건과 혼동하지 않는다.
5. GCC가 원래 소스 위치를 전달하는 줄 표시자다. 포함 지시문이 미처리 상태로 남았다는 뜻이 아니다.
6. 없다. 전처리 뒤 C 번역과 링크가 따로 남아 있다. 사용하는 외부 함수의 정의가 없으면 링크에서 실패할 수 있다.

## 12. 핵심 정리

- 전처리는 토큰과 지시문을 처리하며 실행 중 동작이 아니다.
- include, 매크로 확장, 조건부 포함의 결과를 `.i`로 관찰할 수 있다.
- 주석은 공백으로 바뀌고 문자열 리터럴 내부의 매크로 이름은 확장되지 않는다.
- `.i` 확장자, 줄 표시자, `-E`·`-P`·`-D`는 GCC 구현의 인터페이스다.
