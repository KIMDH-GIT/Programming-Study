# Step 0-9. Part 0 종합 복습

## 1. 학습 목표

- 소스에서 실행까지 각 단계의 입력, 출력, 담당 역할을 스스로 연결한다.
- 한 번에 빌드하는 명령과 단계별 빌드 명령을 직접 재구성한다.
- 대표 실패를 발생 단계와 증거로 분류하고 필요한 수정 범위를 설명한다.
- 빌드 성공, 실행 성공, 요구한 결과의 일치를 독립적으로 검증한다.

## 2. 선수 지식

Part 0의 Step 0-1~0-8을 대상으로 하는 종합 복습이다. 특히 [전체 빌드와 실행](0-7-build-and-run.md), [단계별 오류 구분](0-8-build-errors.md)의 실습 기록을 준비한다. 새로운 자료구조나 고급 C 문법은 사용하지 않는다.

**[GCC/Linux 구현]** GCC와 개발용 표준 라이브러리가 있는 Linux 셸에서 실습한다. 명령은 이번 실습 디렉터리에서 실행한다. 이전 Step의 실행 파일을 재사용하지 않고 이번 소스로 새 결과를 만든다.

## 3. 핵심 개념

Part 0의 핵심은 확장자 순서를 외우는 것이 아니라 **각 단계가 무엇을 확정하고 무엇을 다음 단계로 남기는지** 이해하는 것이다. 전처리 성공은 C 문법의 유효성을 보장하지 않고, C 컴파일 성공은 모든 외부 정의의 존재를 보장하지 않는다. 링크 성공은 실행 환경이나 프로그램의 논리적 정확성을 보장하지 않는다.

| 개념적 작업 | 실습 입력 → 출력 | 여기서 확인할 내용 |
|---|---|---|
| 전처리 | `.c` 및 포함된 헤더 → `.i` | 포함 지시문·매크로 처리 |
| C 컴파일 | `.i` → `.s` | 문법·제약 조건 검사, 대상 코드 생성 |
| 어셈블 | `.s` → `.o` | 명령 인코딩, 심볼·재배치 정보 생성 |
| 링크 | `.o` 및 라이브러리 → 실행 파일 | 외부 참조 연결, 실행 이미지 구성 |
| 실행 요청·로딩 | 실행 파일 → 프로세스 이미지 | 경로·권한·형식·의존 라이브러리 |
| 실행 및 결과 확인 | 프로세스 동작 → 출력·종료 결과 | 요구 사항과 실제 관찰의 일치 |

표의 파일 확장자와 도구별 경계는 **[GCC/Linux 구현]**이다. **[C 표준]** 번역 단계는 논리적 규정이며 이런 파일을 반드시 생성하도록 강제하지 않는다. 표의 마지막 두 행은 빌드 단계가 아니다.

헤더는 선언과 매크로 등을 공유하는 포함 대상이고, 오브젝트는 대상 기계용 코드와 링크 정보 등을 담는다. `#include <stdio.h>`를 처리했다고 표준 라이브러리 함수 구현이 소스에 전부 들어왔다고 설명하면 안 된다. **[GCC/Linux 구현]** 기본 GCC 링크는 필요한 시작 코드와 표준 라이브러리를 연결하도록 구성된다. 동적 링크에서는 일부 실제 주소 결정이나 라이브러리 로딩이 실행 시점에 이루어진다.

## 4. 문법 또는 명령

다음은 모두 **[GCC/Linux 구현]**이다. 우선 전체 빌드·실행을 연결한다.

```sh
gcc -std=c17 -Wall -Wextra -pedantic hello.c -o hello && ./hello
```

이어 단계별로 재구성한다. **한 명령씩** 실행하고 각 명령 직후 상태를 기록한다. 실패하면 중단하고 해당 입력을 확인한다.

```sh
gcc -std=c17 -E hello.c -o hello.i
gcc -std=c17 -Wall -Wextra -pedantic -S hello.i -o hello.s
gcc -c hello.s -o hello.o
gcc hello.o -o hello-staged
./hello-staged
```

상태 기록에 사용할 명령은 다음과 같다. 이것도 직전 명령의 상태를 소비하므로 연속 두 번 읽어 비교하지 않는다.

```sh
printf 'status=%s\n' "$?"
```

`gcc -c hello.c -o hello.o`는 `.c`에서 오브젝트까지 전처리·컴파일·어셈블을 묶어 수행한다. `gcc -c hello.s -o hello.o`는 이미 어셈블리이므로 이 실습에서는 어셈블부터 수행한다. 같은 `-c`라도 입력 종류가 중요하다.

`gcc -### hello.c -o hello`로 GCC가 호출하려는 하위 명령을 볼 수도 있다. `-###`는 실제 하위 명령을 실행하지 않으며 보통 표준 오류에 계획을 표시한다. 이는 선택적 관찰이지 성공 빌드의 증거가 아니다.

## 5. 최소 코드 예제

**[C 표준]** 호스트 환경용 정상 기준 예제다. `hello.c`에 직접 입력한다.

```c
#include <stdio.h>
int main(void)
{
    puts("Part 0 ready");
    return 0;
}
```

정상 표준 출력 환경에서 기대하는 출력은 `Part 0 ready` 한 줄이다. 이 예제는 입출력 실패 처리까지 구현한 프로그램은 아니다.

## 6. 코드 해석

| 줄 | 소스 수준 의미 | 빌드·실행과의 연결 |
|---|---|---|
| 1 | 표준 입출력 헤더 포함 | 전처리로 선언 등을 제공받는다. |
| 2 | `int main(void)` 정의 시작 | 실행 진입에 사용되는 호스트 환경의 함수를 제공한다. |
| 3 | 본문 시작 | 문법 분석 대상이다. |
| 4 | `puts` 호출 | 선언을 바탕으로 호출을 번역하고 라이브러리 구현과 연결한다. |
| 5 | 초기 `main`에서 0 반환 | 성공 종료를 나타내며 실제 호스트 전달 형태는 구현 정의다. |
| 6 | 본문 끝 | 함수 정의를 마친다. |

**[GCC/Linux 구현]** `main`은 일반적으로 실행 파일의 최초 CPU 명령이 아니다. 시작 코드와 런타임 준비를 거쳐 호출된다. 출력 문자열이 바뀌었다고 이미 생성된 실행 파일이 자동으로 갱신되지는 않는다.

## 7. 내부 동작

**번역 관점:** **[C 표준]** 소스 파일과 포함된 내용은 전처리 처리 이후 번역 단위를 이룬다. 외부 함수 참조와 표준 라이브러리 연결까지 포함하여 프로그램이 형성된다. 표준의 개념적 순서를 물리적인 프로세스 수와 동일시하지 않는다.

**도구 관점:** **[GCC/Linux 구현]** GCC 드라이버는 입력 확장자와 옵션으로 시작점·종료점을 정한다. 어셈블러가 만드는 `.o`에는 다른 곳에서 주소가 결정될 부분을 설명하는 재배치 정보가 있을 수 있다. 링커는 오브젝트와 라이브러리의 정의를 찾아 연결한다. `.o`에 코드가 들어 있다는 사실만으로 독립 실행할 수 있는 것은 아니다.

**OS·메모리·CPU 관점:** **[GCC/Linux 구현]** Linux는 보통 ELF 실행 파일의 정보를 바탕으로 가상 주소 공간을 구성하고 실행을 시작한다. 동적 링크된 파일에는 동적 로더를 지정하는 정보가 있을 수 있으며 로더는 필요한 공유 라이브러리를 준비한다. 코드와 데이터가 메모리에 배치된 뒤 CPU가 기계 명령을 실행한다. 이 과정은 C가 Linux·ELF를 요구한다는 뜻이 아니다.

**실패 관점:** **[GCC/Linux 구현]** 전처리의 헤더 오류, C의 문법·제약 조건 진단, 어셈블러 입력 오류, 링커의 정의 누락·중복 정의를 먼저 나눈다. 빌드 뒤에는 실행 경로·권한·ELF 인터프리터·공유 라이브러리 문제를 실행 요청·로딩 범주로, 시작 뒤의 실패를 실행 중 문제로, 요구와 다른 결과를 논리 오류로 분류한다. 동적 심볼 해소는 실행 중 지연될 수 있으므로 시점만 보지 말고 메시지와 담당 구성 요소도 확인한다.

**검증 관점:** **[C 표준]** 문법·제약 조건 위반에는 진단 요구가 있지만, 모든 잘못된 실행이나 요구 사항 위반을 컴파일러가 검출해야 하는 것은 아니다. **[GCC/Linux 구현]** 상태 0과 경고 없음은 유용한 관찰일 뿐 프로그램의 정확성을 증명하지 않는다.

## 8. 자주 하는 실수

- 확장자만 나열하고 각 단계가 맡는 역할을 말하지 못한다. 입력·출력·작업을 한 문장씩 연결한다.
- 헤더와 라이브러리를 같은 것으로 취급한다. 선언 제공과 외부 정의 연결을 분리한다.
- `-o`를 "실행 파일을 만드는 옵션"으로 외운다. `-c ... -o hello.o`에서는 오브젝트 이름을 정한다.
- 이전 Step의 실행 파일을 실행해서 이번 빌드를 검증한다. 디렉터리와 출력 이름을 확인한다.
- 전체 빌드와 단계별 빌드의 실행 파일이 바이트 단위로 같아야 한다고 가정한다. 이번 목표는 같은 소스에 대한 출력·종료 동작 비교다.
- 정의되지 않은 동작의 특정 증상을 시험 통과 조건으로 정한다. Part 0에서는 재현 가능한 명시적 결함을 사용한다.
- Linux 종료 상태 1을 C 표준의 유일한 실패 값이라고 쓴다. 호스트 전달 방식과 표준의 `EXIT_FAILURE`를 구별한다.

## 9. 필수 실습

### Part 0 증거 묶음 작성하기

- **목적:** 각 단계의 산출물과 실제 실행 결과로 전체 흐름을 설명한다.
- **해야 할 일:** 정상 예제를 직접 작성하고 전체 빌드와 단계별 빌드를 각각 수행한다. 각 명령, 입력, 출력 파일, 직후 상태를 표에 기록한다. 두 실행의 출력과 실행 상태를 비교한다. 새 복사본에서 전처리 결함, C 문법 결함, 정의 누락을 각각 하나씩 재현하고 최초 실패 단계를 기록한다. 0-8의 어셈블러·제약 조건·중복 정의 실험 기록을 이번 표와 연결한다. 마지막으로 정상본을 다시 빌드·실행하여 정상 상태를 확인한다.
- **사용할 개념:** 번역 단위, GCC 드라이버, `-E/-S/-c/-o`, 오브젝트, 심볼, 라이브러리, 실행 경로, 종료 상태.
- **예상 관찰 결과:** 정상 경로에서는 중간 파일과 실행 파일을 만들 수 있고 두 실행은 같은 한 줄과 상태 0을 보인다. 결함별로 처음 실패하는 단계가 다르다. 진단 문구와 중간 코드의 모양은 GCC 버전·대상·옵션에 따라 다르다. 이 결과는 **[GCC/Linux 구현]** 관찰이다.
- **확인 포인트:** 파일 생성 여부만이 아니라 명령 성공을 확인했는가? 실패 이후 오래된 산출물을 쓰지 않았는가? 출력과 종료 상태를 별도로 기록했는가? 표준 규정과 환경 관찰에 각각 표식을 붙였는가?

작성 안내와 빈 기록표: [실습 README](../../exercises/00-compilation/0-9/README.md).

## 10. 추가 실습

- ★ **가르치듯 설명하기:** "헤더를 포함했는데 왜 링크가 실패할까?"에 선언·정의·오브젝트·라이브러리 네 단어를 사용해 다섯 문장 이내로 답한다.
- ★★ **드라이버 계획 읽기:** `gcc -### hello.c -o hello`와 `gcc -### -c hello.c -o hello.o`를 비교한다. 실행 계획에서 링크 유무를 찾되 하위 프로그램 이름을 고정된 정답으로 외우지 않는다.
- ★★ **논리 검증 추가:** 정상본의 복사본에서 출력 문자열만 요구와 다르게 바꾸어 빌드한다. 상태 0이어도 요구한 출력과의 비교에서 실패한다는 기록을 남긴다.

## 11. 확인 문제

1. `.c → .i → .s → .o → 실행 파일`의 각 화살표가 맡는 역할은 무엇인가?
2. `.h`를 포함하는 것과 `.o`를 링크하는 것은 어떻게 다른가?
3. `gcc -c hello.c -o hello.o` 뒤 외부 정의 누락이 남을 수 있는가?
4. `-o`만으로 어느 단계에서 멈출지 결정되는가?
5. 파일은 존재하지만 `main` 전에 실행이 실패할 수 있는 Linux 원인 두 가지는?
6. 빌드 성공, 실행 상태 0, 출력 일치를 왜 별도로 확인하는가?
7. 실제 `.i` 파일과 ELF가 존재해야만 C 표준을 준수하는가?

7. 아니다. 물리적인 중간 파일과 특정 실행 형식은 C 표준의 의무가 아니다.

## 12. 핵심 정리

Part 0의 완료 기준은 명령 암기가 아니라 전체 흐름을 직접 실행하고 최초 실패 지점을 증거로 설명하는 것이다. 소스, 헤더, 어셈블리, 오브젝트, 라이브러리, 실행 파일의 역할을 구별하고 빌드·실행·논리 검증을 분리한다.

스스로 다음을 확인하면 Part 0을 마칠 수 있다.

- 전체 빌드·실행과 단계별 빌드를 재현했다.
- 전처리, C 문법·제약 조건, 어셈블러, 링커 정의 누락·중복 정의의 차이를 설명했다.
- 실행 요청·로딩 실패와 실행 중 실패, 논리 오류를 구분했다.
- 표준이 보장한 사실과 Linux에서 관찰한 사실을 구분해 기록했다.

## 13. 다음 Step

**Step 1-1. 첫 프로그램과 `int main(void)`**. Part 0의 빌드·실행 절차를 바탕으로 C 프로그램의 기본 구조를 공부한다. 여기서는 다음 Step의 내용을 미리 확장하지 않는다.
