# Step 0-5. 어셈블러와 `.o` 파일: `gcc -c`

## 1. 학습 목표

- 어셈블러의 입력과 출력을 설명하고 `gcc -c`의 정지 지점을 확인한다.
- 재배치 가능 목적 파일에 기계어 외에 무엇이 필요한지 설명한다.
- 섹션, 심벌, 재배치 정보를 각각 구별한다.
- GNU/Linux 도구로 `.o`를 관찰하되 C 표준의 보장으로 일반화하지 않는다.

## 2. 선수 지식

- Step 0-4의 어셈블리 소스 `.s`, `gcc -S`, 외부 함수 호출
- 선언과 정의가 같지 않다는 점: 헤더는 호출에 필요한 선언을 제공할 수 있다.
- 터미널 명령 실행 및 텍스트 파일 저장

GCC와 GNU Binutils의 `nm`, `objdump`, `readelf`가 있는 GNU/Linux 환경을 가정한다. 출력 형식과 CPU 명령어는 시스템에 따라 다르다.

## 3. 핵심 개념

### 어셈블과 목적 파일

**[GCC/Linux 구현]** 어셈블러(assembler)는 어셈블리 소스의 명령어를 기계어 바이트로 인코딩하고, 지시문을 처리하여 데이터와 메타데이터를 배치한다. `.o`는 보통 **재배치 가능 목적 파일(relocatable object file)**이다. 기계어가 들어 있어도 다른 파일과 연결되기 전이며 최종 실행 주소가 모두 확정된 것은 아니다.

`gcc -c unit.c`는 전처리, 컴파일, 어셈블을 수행하고 링크 전에 멈춘다. `gcc -c unit.s`는 일반적인 소문자 `.s` 입력을 어셈블하며 C 컴파일은 하지 않는다. 따라서 `-c`는 “어셈블러만 실행”을 뜻하는 옵션이 아니라 **링크하지 말고 목적 파일 단계에서 멈추라**는 옵션이다. 중간 `.s`가 작업 디렉터리에 남지 않아도 이상하지 않다. 대문자 `.S`는 전처리가 필요한 어셈블리 입력으로 GCC가 다르게 취급한다.

**[C 표준]** 구현은 여러 번역 단위를 번역하고 필요한 외부 참조와 라이브러리 구성 요소를 연결하여 프로그램을 만든다. 그러나 ELF 형식, `.o` 확장자, 독립적인 어셈블러 명령을 요구하지는 않는다. 여기서 목적 파일은 C의 변수나 데이터 저장 영역을 뜻하는 표준 용어 **객체(object)**와 구별한다.

### 함께 읽어야 하는 세 가지 정보

**[GCC/Linux 구현: ELF GNU/Linux 관찰]** ELF(Executable and Linkable Format)는 목적 파일, 실행 파일, 공유 객체 등에 쓰이는 파일 형식이다. ELF라고 해서 모두 실행 파일은 아니다.

| 용어 | 역할 | 흔히 관찰하는 예 |
|---|---|---|
| 섹션(section) | 같은 성격의 코드, 데이터, 연결용 정보를 묶는다. | `.text`, `.rodata`, `.symtab` |
| 심벌(symbol) | 이름을 정의 위치나 미정의 참조 등과 연결한다. | 이 파일의 `main`, 외부에 필요한 `puts` |
| 재배치(relocation) | 주소 또는 상대 변위 등을 나중에 계산해 적용할 위치와 방식을 기록한다. | 외부 호출 또는 데이터 참조의 수정 위치 |

`.text`에는 보통 명령어, `.rodata`에는 보통 읽기 전용 데이터가 들어간다. 쓰기 가능한 초기화 데이터는 `.data`, 영 초기화 저장 공간은 `.bss`에 배치되는 경우가 많다. `.bss`는 필요한 메모리 크기를 표현하며 그 크기만큼의 0 바이트를 파일에 저장하지 않는 것이 일반적이다. 이런 이름과 배치는 C 표준의 요구가 아니다. 예제에 관련 데이터가 없으면 섹션이 비어 있거나 없을 수 있다.

심벌 표에서 **정의됨(defined)**은 이 파일 등이 제공하는 대상을 뜻하고 **미정의(undefined)**는 이 파일에서 정의를 제공하지 않는 참조를 뜻한다. 미정의 심벌이 있다는 사실만으로 `.o` 생성 실패는 아니다. 다음 단계의 링크에서 다른 목적 파일이나 라이브러리가 이를 제공할 수 있다.

## 4. 문법 또는 명령

`unit.c`를 저장한 디렉터리에서 실행한다.

```sh
gcc -std=c17 -Wall -Wextra -Wpedantic -O0 -S unit.c -o unit.s
gcc -c unit.s -o unit.o
gcc -std=c17 -Wall -Wextra -Wpedantic -O0 -c unit.c -o unit-direct.o
```

첫 경로는 `.s`를 직접 남기고 어셈블한다. 두 번째 경로는 `.c`에서 바로 `.o`까지 진행한다. 동일한 역할을 하는 목적 파일을 만들지만 메타데이터까지 항상 동일하다고 단정하지 않는다.

**[GCC/Linux 구현: GNU Binutils/ELF GNU/Linux 관찰]** 다음은 C 언어 명령이 아닌 파일 조사 도구다.

```sh
readelf -h unit.o
readelf -S unit.o
nm unit.o
readelf -r unit.o
objdump -dr unit.o
```

- `readelf -h`: ELF 헤더를 확인한다. 일반적인 `.o`의 파일 형식은 `REL`(relocatable)이다.
- `readelf -S`: 섹션 표를 확인한다. 대문자 S다.
- `nm`: 심벌을 요약한다. 일반적인 GNU `nm`에서 `T`는 전역 텍스트 심벌, `U`는 미정의 심벌을 나타낸다. 전체 문자 표는 도구 문서를 참고한다.
- `readelf -r`: 재배치 엔트리를 읽는다.
- `objdump -dr`: 기계어를 역어셈블(disassemble)하고 재배치 정보도 함께 보여 준다.

`gcc -S`의 S와 `readelf -S`의 S는 도구가 다르므로 의미도 다르다. `.o`를 텍스트 편집기로 읽거나 `cat`으로 터미널에 출력하지 않는다.

## 5. 최소 코드 예제

`unit.c`:

```c
#include <stdio.h>

int main(void)
{
    puts("object stage");
    return 0;
}
```

**[C 표준]** 호스트 환경의 표준 함수만 사용하는 C17 예제다. 목적 파일 관찰이 목적이므로 함수 분리나 CPU별 인라인 어셈블리는 사용하지 않는다. 예제의 `main`은 이 번역 단위가 정의하고 `puts`의 선언은 헤더가 제공한다.

## 6. 코드 해석

| 줄 | 의미와 관찰 연결 |
|---|---|
| 1 | `puts`의 올바른 선언을 사용할 수 있게 한다. 헤더 포함은 구현의 기계어를 제공하는 것과 다르다. |
| 2 | 빈 줄이다. 명령어를 요구하지 않는다. |
| 3 | `main`을 정의한다. 일반적인 GNU/Linux 목적 파일의 심벌 표에서 이 정의를 확인할 수 있다. |
| 4 | 본문 시작이다. 중괄호 자체가 CPU 명령어인 것은 아니다. |
| 5 | 문자열 데이터와 `puts` 호출이 필요하다. 일반적인 GCC 출력에서는 데이터 참조와 외부 호출 관련 연결 정보를 관찰할 수 있다. |
| 6 | `main`의 반환값을 정한다. 실제 레지스터와 반환 명령은 대상의 응용 프로그램 이진 인터페이스(ABI)에 따른다. |
| 7 | 본문 끝이다. |

**[GCC/Linux 구현: x86-64 GNU/Linux 관찰]** `objdump -dr`에서 호출 명령 근처에 `R_X86_64_PLT32` 같은 재배치 종류가 보일 수 있다. 다른 아키텍처는 다른 이름을 쓰며 같은 아키텍처도 옵션에 따라 달라진다. 이름 암기가 아니라 “이 참조에 후속 계산이 필요하다”는 정보를 읽는다.

## 7. 내부 동작

어셈블러는 레이블을 기록하고 각 명령의 인코딩을 결정하며 섹션별 위치를 계산한다. 같은 섹션 안에서 거리가 확정되는 참조는 직접 계산할 수 있지만, 외부 심벌이나 최종 배치에 의존하는 참조에는 재배치 정보가 필요할 수 있다. 재배치는 미정의 심벌에만 생기는 것이 아니다. 이 파일 안에 정의된 데이터라도 최종 배치를 알아야 하면 필요할 수 있다.

**[GCC/Linux 구현: ELF GNU/Linux 관찰]** 재배치 엔트리는 보통 적용 위치, 재배치 종류, 참조 심벌 정보를 갖는다. 덧셈값(addend)은 형식에 따라 엔트리 또는 적용 대상 데이터에 표현된다. 링커는 이런 정보와 최종 배치를 이용해 값을 계산한다. 지금은 특정 재배치 수식이나 주소를 암기할 필요가 없다.

- **컴파일러/어셈블러 관점:** C 의미를 대상 명령으로 바꾸는 일과 그 명령을 바이트로 인코딩하는 일을 구분한다.
- **CPU 관점:** `.o` 안에 기계어가 있어도 파일 헤더와 심벌 표까지 명령어인 것은 아니다.
- **메모리 관점:** 섹션의 크기나 오프셋은 실행 중 가상 주소와 같은 개념이 아니다. 역어셈블 결과의 작은 주소를 최종 프로세스 주소라고 해석하지 않는다.
- **OS 관점 [GCC/Linux 구현]:** 재배치 가능 ELF 파일은 일반적인 실행 대상으로 완성되지 않았다. 권한 비트가 부족해서만 실행할 수 없는 것이 아니다.

## 8. 자주 하는 실수

- `gcc -c unit.c`가 어셈블만 한다고 설명하기: 입력이 C이므로 앞 단계도 수행한다.
- `.o`를 순수한 기계어 덩어리라고 생각하기: 섹션, 심벌, 재배치 등 연결용 정보도 있다.
- `U puts`를 즉시 컴파일 오류로 판단하기: 외부 정의를 나중에 연결하는 정상 상황일 수 있다.
- `objdump` 출력이 원래 `.s`를 복원한다고 생각하기: 역어셈블은 기계어를 다시 해석하며 원래 주석과 지시문 전체를 복원하지 않는다.
- `chmod +x unit.o`로 실행 파일을 만들려고 하기: 실행 권한 변경은 링크를 대신하지 못한다.
- 섹션 이름이나 x86-64 명령을 모든 C 구현에 적용하기: 모두 이번 GNU/Linux 관찰의 범위다.

## 9. 필수 실습

### 실습 A. 목적 파일의 세 가지 정보 확인

- **목적:** 기계어만으로 설명되지 않는 목적 파일의 구조를 확인한다.
- **해야 할 일:** 예제를 입력하고 4절의 두 경로로 목적 파일을 만든다. `unit.o`의 헤더, 섹션, 심벌, 재배치를 조사한다. `main`과 `puts`의 상태를 구분하고 재배치 엔트리 하나가 어떤 참조와 관련되는지 찾아본다.
- **사용할 개념:** `-c`, 재배치 가능 목적 파일, ELF, 섹션, 정의/미정의 심벌, 재배치
- **예상 관찰 결과:** `.o` 생성은 성공하며 일반적인 GNU/Linux 환경에서 `REL`, 코드 섹션, 정의된 `main`, 미정의 `puts`와 재배치 정보가 보인다. 개수와 주소는 고정되지 않는다.
- **확인 포인트:** “`puts`가 미정의인데 왜 `.o` 생성은 성공했는가?”에 답한다. `.o`에서 보이는 오프셋을 실행 주소라고 단정하지 않았는지 확인한다.

## 10. 추가 실습

- **★ 기초:** `nm unit.o`와 `nm unit-direct.o`를 비교하여 핵심 정의와 참조가 같은지 확인한다. 파일 전체의 일치 여부는 통과 기준이 아니다.
- **★★ 확장:** 작업용 소스 복사본에서 `puts` 호출 한 줄만 제거하고 새 목적 파일을 만든다. 미정의 심벌과 재배치 정보가 어떻게 달라지는지 비교한다. 호출이 없어도 다른 목적의 재배치 엔트리는 남을 수 있다.

## 11. 확인 문제

1. `gcc -c unit.c`와 `gcc -c unit.s`는 어떤 단계를 수행하는가?
2. 재배치 가능 목적 파일을 실행 파일과 구별하는 핵심 이유는 무엇인가?
3. 섹션, 심벌, 재배치는 각각 어떤 정보를 제공하는가?
4. `nm`의 `U puts`는 무엇을 뜻하며 항상 오류인가?
5. 파일 내부에 정의된 대상에 대한 참조에도 재배치가 필요할 수 있는가?

<details>
<summary>정답과 해설 펼치기</summary>

1. `.c`는 전처리, 컴파일, 어셈블을 수행한다. 소문자 `.s`는 어셈블한다. 둘 다 링크 전에 멈춘다.
2. 기계어는 있지만 다른 구성 요소와의 연결과 최종 배치 등이 아직 완료되지 않았다.
3. 섹션은 내용을 성격별로 묶고, 심벌은 이름과 정의 또는 참조를 연결하며, 재배치는 후속 계산을 적용할 위치와 방식을 기록한다.
4. 해당 목적 파일이 `puts`의 정의를 제공하지 않는다는 뜻이다. 라이브러리 등에서 정의를 연결할 예정이라면 정상이다.
5. 가능하다. 파일 내부 데이터여도 최종 배치에 의존하는 참조는 후속 계산이 필요할 수 있다.

</details>

## 12. 핵심 정리

- `gcc -c`는 입력에 필요한 앞 단계를 수행하고 링크 전에 멈춘다.
- `.o`는 기계어와 연결 정보를 담는 재배치 가능 목적 파일이다.
- 심벌의 미정의 상태와 컴파일 실패는 같은 말이 아니다.
- **[GCC/Linux 구현]** ELF, `nm`, `objdump`, `readelf`의 관찰을 **[C 표준]**의 요구로 일반화하지 않는다.
