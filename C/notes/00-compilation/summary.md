
# Step 0-1. 전체 컴파일 과정 개요

## 핵심 개념
소스(source): 사람이 작성한 C 텍스트

번역(translation): 이 텍스트를 실행 가능한 프로그램으로 만드는 과정

빌드(build): 보통 번역과 링크를 포함하는 작업

실행(execution): 만들어진 프로그램의 동작

`gcc`: 전처리기, 컴파일러, 어셈블러, 링커를 조정하는 드라이버(driver)

```text
hello.c --전처리--> hello.i --컴파일--> hello.s --어셈블--> hello.o --링크--> hello
```
목적 파일: 단순한 기계 명령 바이트의 나열이 아니라 아직 정해지지 않은 주소 등을 처리하기 위한 정보도 포함함.
링크: 목적 파일과 필요한 라이브러리 등을 연결하는 과정


| 산출물 | 의미 | 그 자체를 프로그램으로 실행하는가? |
|---|---|---|
| `.c` | C 소스 텍스트 | 아니오 |
| `.i` | 전처리된 C 입력 | 아니오 |
| `.s` | 대상 CPU용 어셈블리 텍스트 | 아니오 |
| `.o` | 기계 코드와 심볼·재배치 정보 등을 담은 목적 파일(object file) | 보통 아니오 |
| `hello` | 링크된 실행 파일 | 지원되는 실행 환경에서 실행 |


## 명령

- `-E`: 전처리 후 멈춘다. `-o`가 없으면 결과를 보통 표준 출력으로 보낸다.
- `-S`: 어셈블리 생성 후 멈춘다. GCC는 `.i`를 전처리된 C 입력으로 취급한다.
- `-c`: 어셈블까지 수행하고 링크는 하지 않는다.(기계어 형태) `.s` 입력이면 C 전처리·컴파일은 필요 없다.
- `-o 파일명`: 출력 이름을 정한다. 단계 선택 옵션이 아니다.
- `./hello`: 현재 디렉터리의 실행 파일을 실행한다. GCC 옵션이 아닌 셸 명령이다.


실행 시에는 OS의 로더와, 동적 링크된 경우 동적 링커가 관여한다. 
CPU는 준비된 프로그램의 기계 명령을 수행한다. 
CPU가 #include를 읽거나 실행 중에 C 소스를 자동 번역하는 구조가 아니다. 
시작 코드가 main 호출을 준비하므로 main이 실행 파일의 첫 기계 명령이라고 단정해서도 안 된다.




# Step 0-2. C 소스 `.c`와 헤더 `.h`


##  핵심 개념

### 소스와 헤더의 역할


`.c` 파일은 보통 함수 정의 등 구현을 작성하고 개별 컴파일 입력으로 준다. 
`.h` 파일에는 여러 소스가 공유할 함수 선언, 타입 선언, 매크로 정의 등을 둔다. 
헤더는 보통 다른 소스에서 포함하며 **독립 번역 단위로 직접 컴파일하지 않는다.** GCC가 헤더 입력으로 미리 컴파일된 헤더를 만드는 기능은 별도 기능이지 일반적인 프로그램 빌드 절차가 아니다.

(Include Guard)는 C 및 C++ 프로그래밍에서 동일한 헤더 파일이 중복으로 포함되어 발생하는 컴파일 오류를 방지하기 위해 사용하는 전리기(Preprocessor) 기법
ex) #ifndef / #define / #endif 방식: 헤더 파일의 맨 처음과 끝에 매크로 조건을 추가

### 선언과 정의


선언은 이름과 타입 등의 정보를 알린다. 
정의는 함수의 본문이나 객체의 저장 공간을 제공하는 선언이다. 따라서 정의도 선언의 일종이다.

- `int answer(void);`는 인수 없이 `int`를 반환하는 함수의 선언이며 본문이 없다.
- `int answer(void) { return 42; }`는 그 함수의 정의다.


모든 정의를 헤더에서 금지한다는 규칙도 정확하지 않다. 매크로와 타입 정의는 흔히 헤더에 둔다. 
다만 이 단계에서는 외부 연결을 갖는 일반 함수 본문이나 `int count = 0;` 같은 객체 정의를 헤더에 두지 않는다. 여러 번역 단위에 중복 정의가 생길 수 있다. 


`<...>` 형식은 구현 정의의 장소에서 헤더를 검색한다. 
`"..."` 형식은 구현 정의의 방식으로 소스 파일을 검색하며, 지원되지 않거나 검색에 실패하면 `<...>` 형식으로 다시 처리한다. 


## 문법 또는 명령

```c
#include <stdio.h>
#include "message.h"
```

표준 헤더는 보통 `<...>`로 헤더파일이 라이브러리로 등록되어 내부에서 경로를 인식하고, 프로젝트 헤더는 보통 `"..."`로 Cmake 설정으로 링커가 라이브러리로 등록하여 쓴다. 
사용자가 직접 프로젝트 라이브러리로 등록해서 <>로 쓸 수 있다.

라이브러리로 등록하면 "../include/math.h"처럼 안쓰고 어디서든 <math> 처럼 쓸 수 있다.
#include "경로" 에서 include가 문자열이 가리키는 경로의 파일을 가져오게 됨


이것은 적절한 관례이지 두 형태가 파일 종류를 엄격히 분류한다는 뜻은 아니다. 지시문 끝에 세미콜론을 붙이지 않는다.

`main.c`와 `message.h`가 같은 디렉터리에 있을 때:


## 최소 코드 예제

관찰용 `message.h`:

```c
#ifndef STUDY_MESSAGE_H
#define STUDY_MESSAGE_H

#define COURSE_MESSAGE "C17 headers"

#endif
```

관찰용 `main.c`:

```c
#include <stdio.h>
#include "message.h"

int main(void)
{
    puts(COURSE_MESSAGE);
    return 0;
}
```

## 내부 동작

include는 실행 시 파일을 읽는 함수 호출이 아니다. 전처리 시 지정한 헤더·소스 파일의 내용으로 지시문을 대체하고 그 내용도 전처리한다. 따라서 guard의 상태는 프로그램 메모리의 런타임 플래그가 아니라 전처리 중의 매크로 정의 상태다.
같은 구현을 별도 입력에도 넣으면 중복 정의가 생길 수 있다.
