
# Step 0-1. 전체 컴파일 과정 개요

## 핵심 개념
소스(source): 사람이 작성한 C 텍스트

번역(translation): 이 텍스트를 실행 가능한 프로그램으로 만드는 과정

빌드(build): 보통 번역과 링크를 포함하는 작업

실행(execution): 만들어진 프로그램의 동작

`gcc`: 전처리기, 컴파일러, 어셈블러, 링커를 조정하는 드라이버(driver)

```text
hello.c --전처리--> hello.i --컴파일--> hello.s --어셈블--> hello.o --링크--> hello
```
목적 파일: 단순한 기계 명령 바이트의 나열이 아니라 아직 정해지지 않은 주소 등을 처리하기 위한 정보도 포함함.
링크: 목적 파일과 필요한 라이브러리 등을 연결하는 과정


| 산출물 | 의미 | 그 자체를 프로그램으로 실행하는가? |
|---|---|---|
| `.c` | C 소스 텍스트 | 아니오 |
| `.i` | 전처리된 C 입력 | 아니오 |
| `.s` | 대상 CPU용 어셈블리 텍스트 | 아니오 |
| `.o` | 기계 코드와 심볼·재배치 정보 등을 담은 목적 파일(object file) | 보통 아니오 |
| `hello` | 링크된 실행 파일 | 지원되는 실행 환경에서 실행 |


## 명령

- `-E`: 전처리 후 멈춘다. `-o`가 없으면 결과를 보통 표준 출력으로 보낸다.
- `-S`: 어셈블리 생성 후 멈춘다. GCC는 `.i`를 전처리된 C 입력으로 취급한다.
- `-c`: 어셈블까지 수행하고 링크는 하지 않는다.(기계어 형태) `.s` 입력이면 C 전처리·컴파일은 필요 없다.
- `-o 파일명`: 출력 이름을 정한다. 단계 선택 옵션이 아니다.
- `./hello`: 현재 디렉터리의 실행 파일을 실행한다. GCC 옵션이 아닌 셸 명령이다.


실행 시에는 OS의 로더와, 동적 링크된 경우 동적 링커가 관여한다. 
CPU는 준비된 프로그램의 기계 명령을 수행한다. 
CPU가 #include를 읽거나 실행 중에 C 소스를 자동 번역하는 구조가 아니다. 
시작 코드가 main 호출을 준비하므로 main이 실행 파일의 첫 기계 명령이라고 단정해서도 안 된다.




# Step 0-2. C 소스 `.c`와 헤더 `.h`


##  핵심 개념

### 소스와 헤더의 역할


`.c` 파일은 보통 함수 정의 등 구현을 작성하고 개별 컴파일 입력으로 준다. 
`.h` 파일에는 여러 소스가 공유할 함수 선언, 타입 선언, 매크로 정의 등을 둔다. 
헤더는 보통 다른 소스에서 포함하며 **독립 번역 단위로 직접 컴파일하지 않는다.** GCC가 헤더 입력으로 미리 컴파일된 헤더를 만드는 기능은 별도 기능이지 일반적인 프로그램 빌드 절차가 아니다.

(Include Guard)는 C 및 C++ 프로그래밍에서 동일한 헤더 파일이 중복으로 포함되어 발생하는 컴파일 오류를 방지하기 위해 사용하는 전리기(Preprocessor) 기법
ex) #ifndef / #define / #endif 방식: 헤더 파일의 맨 처음과 끝에 매크로 조건을 추가

### 선언과 정의


선언은 이름과 타입 등의 정보를 알린다. 
정의는 함수의 본문이나 객체의 저장 공간을 제공하는 선언이다. 따라서 정의도 선언의 일종이다.

- `int answer(void);`는 인수 없이 `int`를 반환하는 함수의 선언이며 본문이 없다.
- `int answer(void) { return 42; }`는 그 함수의 정의다.


모든 정의를 헤더에서 금지한다는 규칙도 정확하지 않다. 매크로와 타입 정의는 흔히 헤더에 둔다. 
다만 이 단계에서는 외부 연결을 갖는 일반 함수 본문이나 `int count = 0;` 같은 객체 정의를 헤더에 두지 않는다. 여러 번역 단위에 중복 정의가 생길 수 있다. 


`<...>` 형식은 구현 정의의 장소에서 헤더를 검색한다. 
`"..."` 형식은 구현 정의의 방식으로 소스 파일을 검색하며, 지원되지 않거나 검색에 실패하면 `<...>` 형식으로 다시 처리한다. 


## 문법 또는 명령

```c
#include <stdio.h>
#include "message.h"
```

표준 헤더는 보통 `<...>`로 헤더파일이 라이브러리로 등록되어 내부에서 경로를 인식하고, 프로젝트 헤더는 보통 `"..."`로 Cmake 설정으로 링커가 라이브러리로 등록하여 쓴다. 
사용자가 직접 프로젝트 라이브러리로 등록해서 <>로 쓸 수 있다.

라이브러리로 등록하면 "../include/math.h"처럼 안쓰고 어디서든 <math> 처럼 쓸 수 있다.
#include "경로" 에서 include가 문자열이 가리키는 경로의 파일을 가져오게 됨


이것은 적절한 관례이지 두 형태가 파일 종류를 엄격히 분류한다는 뜻은 아니다. 지시문 끝에 세미콜론을 붙이지 않는다.

`main.c`와 `message.h`가 같은 디렉터리에 있을 때:


## 최소 코드 예제

관찰용 `message.h`:

```c
#ifndef STUDY_MESSAGE_H
#define STUDY_MESSAGE_H

#define COURSE_MESSAGE "C17 headers"

#endif
```

관찰용 `main.c`:

```c
#include <stdio.h>
#include "message.h"

int main(void)
{
    puts(COURSE_MESSAGE);
    return 0;
}
```

## 내부 동작

include는 실행 시 파일을 읽는 함수 호출이 아니다. 전처리 시 지정한 헤더·소스 파일의 내용으로 지시문을 대체하고 그 내용도 전처리한다. 따라서 guard의 상태는 프로그램 메모리의 런타임 플래그가 아니라 전처리 중의 매크로 정의 상태다.
같은 구현을 별도 입력에도 넣으면 중복 정의가 생길 수 있다.



# Step 0-3. 전처리기와 `.i` 파일: `gcc -E`


## 핵심 개념




| 기능 | 대표 형태 | 전처리 결과 |
|---|---|---|
| 소스 파일 포함 | `#include "message.h"` | 지정한 내용이 포함되고 그 안의 지시문도 처리된다. |
| 객체형 매크로 정의 | `#define MESSAGE "ready"` | 이후 `MESSAGE` 전처리 토큰을 치환할 규칙이 생긴다. |
| 조건부 포함 | `#if defined(VERBOSE)` | 조건에 맞는 그룹을 남기고 다른 그룹은 제외한다. |

매크로는 C 변수가 아니다. 타입이나 런타임 저장 공간을 갖지 않으며, 정의 지점 이후의 토큰 처리에 영향을 준다. 치환 결과는 추가 매크로 확장 여부를 다시 검사한다. 전처리는 토큰 단위이므로 식별자 일부나 문자열 리터럴 안의 글자를 임의로 치환하지 않는다. `MESSAGE`는 확장되지만 `"MESSAGE"`는 그대로 문자열이고 `MESSAGE_COUNT`는 다른 식별자다.



### 조건부 포함은 실행 중 분기가 아니다

`#if`·`#ifdef`는 빌드할 때 어떤 토큰을 뒤 단계에 전달할지 정한다. 런타임 변수나 사용자 입력을 읽어 결정하는 C의 `if` 문과 다르다. `#if defined(VERBOSE)`는 매크로가 **정의되어 있는가**만 묻는다. 값이 0으로 정의되어 있어도 참이다. 숫자 값을 검사하려면 `#if VERBOSE`처럼 다른 조건을 써야 한다.

### `.i` 파일은 무엇인가?

**[GCC/Linux 구현]** `gcc -E`는 전처리에서 멈추며 기본적으로 표준 출력에 텍스트를 쓴다. `-o main.i`로 저장한 `.i`는 GCC가 전처리된 C 입력으로 인식하는 파일이다. `.i`는 실행 파일도 어셈블리도 아니다. 포함한 시스템 헤더 때문에 원본보다 훨씬 길 수 있다.

**[C 표준]** `.i`라는 파일 형식이나 확장자를 요구하지 않는다. GCC의 출력에는 위치 추적용 줄 표시자와 구현별 선언·확장 표기가 보일 수 있다. 

## 최소 코드 예제

관찰용 `main.c`:

```c
#include <stdio.h>
#define MESSAGE "preprocessing"

int main(void)
{
    /* MESSAGE inside this comment is not output. */
    puts(MESSAGE);
    puts("MESSAGE");
    return 0;
}
```

정상적인 출력 환경에서 결과는 두 줄이다.

```text
preprocessing
MESSAGE
```

이 예제는 객체형 매크로의 기본 확장을 보여 준다. 조건부 포함을 추가하는 필수 실습의 완성 코드는 제공하지 않는다.



# Step 0-4. 컴파일러와 `.s` 파일: `gcc -S`


## 핵심 개념

### 컴파일이라는 말의 두 범위

일상적으로는 소스에서 실행 파일까지 만드는 전체 작업을 “컴파일”이라고 부르기도 한다. 여기서는 전처리된 C를 분석하여 어셈블리 소스를 생성하는 **좁은 의미의 컴파일**에 집중한다. GCC의 `gcc` 명령은 여러 도구를 연결하는 **컴파일러 드라이버**이므로 명령 이름만 보고 어디까지 진행했는지 판단하면 안 된다.

**[C 표준]** C는 식, 문장, 형식, 함수 호출 등의 의미와 번역 과정의 요구 사항을 규정한다. 번역 단위(translation unit)는 전처리를 거쳐 남은 소스이며, 포함된 헤더의 내용도 반영된다. 표준의 개념적 번역 단계가 실제 도구의 프로세스나 중간 파일과 일대일로 대응할 필요는 없다. `.s` 파일을 반드시 디스크에 만들라는 요구도 없다.

**[GCC/Linux 구현]** `gcc -S hello.c`는 필요한 전처리와 컴파일을 수행한 뒤 어셈블 전에 멈춘다. 출력인 `hello.s`는 대상 CPU와 어셈블러 문법에 맞춘 **텍스트 형태의 어셈블리 소스**다. 이미 전처리된 `hello.i`를 입력하면 GCC는 확장자를 보고 전처리가 끝난 C 소스로 취급한다.

### 컴파일러가 판단하는 것

컴파일러는 토큰을 문법 구조로 묶고 선언 및 형식 관계를 검사한 뒤 프로그램의 의미를 기계에서 수행할 연산으로 바꾼다. 이름을 잘못 썼거나 문법이 깨진 경우 이 과정에서 진단이 발생할 수 있다. 컴파일 성공은 모든 버그의 부재나 외부 함수 정의의 존재를 보증하지 않는다. 외부 정의 연결은 뒤의 링크 단계에서 필요할 수 있다.

**[C 표준]** 관찰 가능한 동작을 보존하는 범위에서 구현은 연산을 바꾸거나 없앨 수 있다. 이를 흔히 **as-if 규칙**이라고 설명한다. “작성한 각 줄이 반드시 명령어 하나가 된다”는 규칙은 없다.

**[GCC/Linux 구현]** 최적화 옵션, GCC 버전, 대상 CPU, 배포판의 기본 보안 옵션에 따라 `.s`의 내용이 달라진다. `-O0`는 관찰용으로 유용하지만 모든 내부 변환을 끄거나 원문과 일대일 대응을 보장하지 않는다.

## 문법 또는 명령

다음 명령은 `hello.c`를 저장한 디렉터리에서 실행한다.

```sh
gcc --version
gcc -dumpmachine
gcc -std=c17 -Wall -Wextra -Wpedantic -O0 -S hello.c -o hello.s
less hello.s
```





# Step 0-5. 어셈블러와 `.o` 파일: `gcc -c`


## 핵심 개념

### 어셈블과 목적 파일

**[GCC/Linux 구현]** 어셈블러(assembler)는 어셈블리 소스의 명령어를 기계어 바이트로 인코딩하고, 지시문을 처리하여 데이터와 메타데이터를 배치한다. `.o`는 보통 **재배치 가능 목적 파일(relocatable object file)**이다. 기계어가 들어 있어도 다른 파일과 연결되기 전이며 최종 실행 주소가 모두 확정된 것은 아니다.

`gcc -c unit.c`는 전처리, 컴파일, 어셈블을 수행하고 링크 전에 멈춘다. `gcc -c unit.s`는 일반적인 소문자 `.s` 입력을 어셈블하며 C 컴파일은 하지 않는다. 따라서 `-c`는 “어셈블러만 실행”을 뜻하는 옵션이 아니라 **링크하지 말고 목적 파일 단계에서 멈추라**는 옵션이다. 중간 `.s`가 작업 디렉터리에 남지 않아도 이상하지 않다. 대문자 `.S`는 전처리가 필요한 어셈블리 입력으로 GCC가 다르게 취급한다.

**[C 표준]** 구현은 여러 번역 단위를 번역하고 필요한 외부 참조와 라이브러리 구성 요소를 연결하여 프로그램을 만든다. 그러나 ELF 형식, `.o` 확장자, 독립적인 어셈블러 명령을 요구하지는 않는다. 여기서 목적 파일은 C의 변수나 데이터 저장 영역을 뜻하는 표준 용어 **객체(object)**와 구별한다.

### 함께 읽어야 하는 세 가지 정보

**[GCC/Linux 구현: ELF GNU/Linux 관찰]** ELF(Executable and Linkable Format)는 목적 파일, 실행 파일, 공유 객체 등에 쓰이는 파일 형식이다. ELF라고 해서 모두 실행 파일은 아니다.

| 용어 | 역할 | 흔히 관찰하는 예 |
|---|---|---|
| 섹션(section) | 같은 성격의 코드, 데이터, 연결용 정보를 묶는다. | `.text`, `.rodata`, `.symtab` |
| 심벌(symbol) | 이름을 정의 위치나 미정의 참조 등과 연결한다. | 이 파일의 `main`, 외부에 필요한 `puts` |
| 재배치(relocation) | 주소 또는 상대 변위 등을 나중에 계산해 적용할 위치와 방식을 기록한다. | 외부 호출 또는 데이터 참조의 수정 위치 |

`.text`에는 보통 명령어, `.rodata`에는 보통 읽기 전용 데이터가 들어간다. 쓰기 가능한 초기화 데이터는 `.data`, 영 초기화 저장 공간은 `.bss`에 배치되는 경우가 많다. `.bss`는 필요한 메모리 크기를 표현하며 그 크기만큼의 0 바이트를 파일에 저장하지 않는 것이 일반적이다. 이런 이름과 배치는 C 표준의 요구가 아니다. 예제에 관련 데이터가 없으면 섹션이 비어 있거나 없을 수 있다.

심벌 표에서 **정의됨(defined)**은 이 파일 등이 제공하는 대상을 뜻하고 **미정의(undefined)**는 이 파일에서 정의를 제공하지 않는 참조를 뜻한다. 미정의 심벌이 있다는 사실만으로 `.o` 생성 실패는 아니다. 다음 단계의 링크에서 다른 목적 파일이나 라이브러리가 이를 제공할 수 있다.

## 문법 또는 명령

`unit.c`를 저장한 디렉터리에서 실행한다.

```sh
gcc -std=c17 -Wall -Wextra -Wpedantic -O0 -S unit.c -o unit.s
gcc -c unit.s -o unit.o
gcc -std=c17 -Wall -Wextra -Wpedantic -O0 -c unit.c -o unit-direct.o
```

첫 경로는 `.s`를 직접 남기고 어셈블한다. 두 번째 경로는 `.c`에서 바로 `.o`까지 진행한다. 동일한 역할을 하는 목적 파일을 만들지만 메타데이터까지 항상 동일하다고 단정하지 않는다.

**[GCC/Linux 구현: GNU Binutils/ELF GNU/Linux 관찰]** 다음은 C 언어 명령이 아닌 파일 조사 도구다.

```sh
readelf -h unit.o
readelf -S unit.o
nm unit.o
readelf -r unit.o
objdump -dr unit.o
```

- `readelf -h`: ELF 헤더를 확인한다. 일반적인 `.o`의 파일 형식은 `REL`(relocatable)이다.
- `readelf -S`: 섹션 표를 확인한다. 대문자 S다.
- `nm`: 심벌을 요약한다. 일반적인 GNU `nm`에서 `T`는 전역 텍스트 심벌, `U`는 미정의 심벌을 나타낸다. 전체 문자 표는 도구 문서를 참고한다.
- `readelf -r`: 재배치 엔트리를 읽는다.
- `objdump -dr`: 기계어를 역어셈블(disassemble)하고 재배치 정보도 함께 보여 준다.

`gcc -S`의 S와 `readelf -S`의 S는 도구가 다르므로 의미도 다르다. `.o`를 텍스트 편집기로 읽거나 `cat`으로 터미널에 출력하지 않는다.

## 최소 코드 예제

`unit.c`:

```c
#include <stdio.h>

int main(void)
{
    puts("object stage");
    return 0;
}
```

**[C 표준]** 호스트 환경의 표준 함수만 사용하는 C17 예제다. 목적 파일 관찰이 목적이므로 함수 분리나 CPU별 인라인 어셈블리는 사용하지 않는다. 예제의 `main`은 이 번역 단위가 정의하고 `puts`의 선언은 헤더가 제공한다.

## 코드 해석

| 줄 | 의미와 관찰 연결 |
|---|---|
| 1 | `puts`의 올바른 선언을 사용할 수 있게 한다. 헤더 포함은 구현의 기계어를 제공하는 것과 다르다. |
| 2 | 빈 줄이다. 명령어를 요구하지 않는다. |
| 3 | `main`을 정의한다. 일반적인 GNU/Linux 목적 파일의 심벌 표에서 이 정의를 확인할 수 있다. |
| 4 | 본문 시작이다. 중괄호 자체가 CPU 명령어인 것은 아니다. |
| 5 | 문자열 데이터와 `puts` 호출이 필요하다. 일반적인 GCC 출력에서는 데이터 참조와 외부 호출 관련 연결 정보를 관찰할 수 있다. |
| 6 | `main`의 반환값을 정한다. 실제 레지스터와 반환 명령은 대상의 응용 프로그램 이진 인터페이스(ABI)에 따른다. |
| 7 | 본문 끝이다. |

**[GCC/Linux 구현: x86-64 GNU/Linux 관찰]** `objdump -dr`에서 호출 명령 근처에 `R_X86_64_PLT32` 같은 재배치 종류가 보일 수 있다. 다른 아키텍처는 다른 이름을 쓰며 같은 아키텍처도 옵션에 따라 달라진다. 이름 암기가 아니라 “이 참조에 후속 계산이 필요하다”는 정보를 읽는다.





# Step 0-6. 링커·라이브러리와 실행 파일


## 핵심 개념

### 링커는 무엇을 연결하는가?

**[GCC/Linux 구현]** 링커(linker)는 목적 파일과 필요한 라이브러리 입력을 읽어 심벌 참조를 정의와 연결하고, 출력의 코드/데이터 배치를 정하며, 가능한 재배치를 적용한다. 결과는 보통 실행 파일이지만 링커 옵션에 따라 공유 객체나 다른 재배치 가능 파일도 만들 수 있다. 단순히 여러 파일의 바이트를 순서대로 이어 붙이는 작업은 아니다.

**[C 표준]** 번역 단계에는 외부 참조를 해결하고 필요한 라이브러리 구성 요소를 연결하는 개념이 있다. 하지만 특정 링커 프로그램, ELF 파일, `.a` 또는 `.so` 확장자는 정하지 않는다. 실행 환경은 호스트 환경과 독립 환경(freestanding environment)으로 구분된다. 여기서는 표준 라이브러리와 `main`을 갖는 호스트 환경을 다룬다.

### 헤더는 사용 규약, 라이브러리는 구현

`#include <stdio.h>`를 통해 컴파일러는 `puts`의 선언 등 인터페이스를 알 수 있다. 일반적인 GNU/Linux 환경에서 `puts`의 실제 구현은 C 라이브러리(libc)가 제공한다. 헤더에 함수 정의가 들어가는 경우도 있지만, **표준 헤더 포함과 외부 라이브러리의 기계어 연결은 같은 작업이 아니다.**

**[GCC/Linux 구현]** 일반적인 `gcc hello.o -o hello`는 GCC 드라이버가 시작 코드와 기본 라이브러리 등을 링크 입력에 추가한다. 그래서 이 예제에서는 직접 `-lc`를 적지 않아도 된다. 반면 모든 외부 라이브러리가 자동 추가되는 것은 아니다. `ld hello.o -o hello`를 같은 뜻으로 사용하면 GCC가 마련하는 입력과 설정이 빠질 수 있다.

### 정적 라이브러리와 공유 라이브러리

**[GCC/Linux 구현: GNU/Linux 관찰]** 다음 비교는 GNU 계열 링크 환경의 일반적인 방식이다.

| 구분 | 정적 라이브러리(static library) | 공유 라이브러리(shared library) |
|---|---|---|
| 흔한 파일 | `libname.a` | `libname.so`, 버전이 붙은 `.so` |
| 형태 | 목적 파일들을 모은 아카이브 | 동적 연결에 쓰이는 공유 객체 |
| 일반적인 링크 시 처리 | 필요한 정의를 제공하는 멤버를 선택하여 출력에 포함 | 필요한 공유 객체와 동적 심벌 연결 정보를 출력에 기록 |
| 실행 시 요구 | 포함된 라이브러리 부분에는 원래 `.a`가 필요하지 않음 | 호환되는 공유 라이브러리를 로더가 찾을 수 있어야 함 |
| 변경의 영향 | 라이브러리 변경을 반영하려면 보통 다시 링크 | 호환성과 검색 경로가 맞아야 교체된 라이브러리를 이용할 수 있음 |

아카이브의 일부 멤버만 선택되는 것과 그 멤버 안의 불필요한 코드가 모두 제거되는 것은 다른 문제다. 정적 라이브러리 하나를 연결했다고 실행 파일 전체가 완전 정적 연결이 되는 것도 아니다. 예를 들어 사용자 `.a`의 코드는 포함하면서 libc는 공유 라이브러리를 사용할 수 있다.

공유 연결도 빌드 시 링커가 수행하는 작업이다. 일부 주소 확정과 재배치는 실행 시의 동적 링커/로더에 남길 수 있다. “공유 라이브러리는 링크할 때 전혀 검사하지 않는다”거나 “실행 파일에 관련 정보가 전혀 없다”는 설명은 틀리다.

## 내부 동작

### 빌드 시: 이름과 배치 연결

**[GCC/Linux 구현: ELF GNU/Linux 관찰]** 링커는 입력 섹션을 출력 섹션 등에 배치하고 심벌 정의를 찾으며 재배치 계산을 적용한다. 실행 파일의 **프로그램 헤더(program header)**는 로더가 메모리를 구성할 때 사용할 **세그먼트(segment)**를 설명한다. 앞 Step에서 본 섹션이 링크 관점의 분류라면, 세그먼트는 실행 시 적재 관점의 묶음이다. 한 세그먼트에 여러 섹션이 포함될 수 있다.

### 실행 시: 프로세스 준비와 시작 코드

**[C 표준]** 호스트 환경에서는 `main`을 통해 프로그램이 시작되며, 처음 호출된 `main`에서 반환하면 해당 값을 인수로 `exit`를 호출하는 것과 같은 효과가 있다. `main`보다 앞선 OS 진입 주소나 `_start`라는 심벌은 C 표준의 요구가 아니다. 독립 환경의 시작 방식은 구현 정의다.

**[GCC/Linux 구현: GNU/Linux 관찰]** `./hello`를 실행하면 셸이 OS에 프로그램 실행을 요청한다. 커널은 실행 파일의 정보를 바탕으로 주소 공간을 준비한다. 동적 연결 프로그램에 지정된 인터프리터가 있으면 동적 로더도 관여하여 공유 객체를 적재하고 필요한 재배치 등을 처리한다. 함수 심벌 연결의 일부는 설정에 따라 첫 호출까지 늦춰질 수도 있다.

그 뒤 실행 파일의 시작 코드가 C 실행 환경 초기화와 `main` 호출을 이어 준다. 흔히 시작 코드의 심벌 이름이 `_start`이며 glibc 환경에서는 `__libc_start_main` 같은 구성 요소가 관여한다. 동적 연결 프로그램에서 CPU가 가장 먼저 실행하는 사용자 코드가 반드시 실행 파일의 `_start`라는 뜻은 아니다. 동적 로더가 먼저 실행될 수 있다.

- **CPU 관점:** 준비된 메모리의 기계어를 실행하며 C의 함수 이름 자체를 해석하지 않는다.
- **메모리/OS 관점:** 실행 파일은 프로세스 자체가 아니라 프로세스 생성에 쓰이는 파일이다. 동적 로더, 메모리 매핑과 런타임 준비가 추가로 필요할 수 있다.
- **학습 경계:** 시작 코드의 역할까지만 이해한다. 레지스터별 호출 규약, PLT/GOT의 세부 구조와 직접 작성하는 시작 코드는 여기서 다루지 않는다.





# Step 0-7. 전체 빌드와 실행


## 핵심 개념

**빌드(build)**는 소스로부터 실행 가능한 결과물을 만드는 작업이다. 여기서는 GCC 드라이버가 전처리, 좁은 의미의 컴파일, 어셈블, 링크를 조정한다. **실행(run)**은 그 결과물을 운영체제에 실행 요청하는 별도 작업이다. GCC는 빌드에 성공했다고 프로그램까지 실행하지 않는다.

**[C 표준]** 번역 단계는 프로그램을 해석하는 논리적 모형이다. 실제로 `.i`, `.s`, `.o` 파일을 디스크에 남기거나 네 개의 별도 프로그램을 실행해야 한다는 규정은 없다. 호스트 환경의 `main`과 표준 입출력 함수의 의미는 규정하지만 `gcc`, 파일 확장자, 실행 파일 이름은 규정하지 않는다.

**[GCC/Linux 구현]** `gcc`는 C 소스뿐 아니라 오브젝트 파일도 입력받는 드라이버다. 단계 중단 옵션 없이 C 파일을 입력하면 보통 링크까지 수행한다. `-o hello`는 최종 출력 이름을 정하며, 실행 명령이 아니다. 기본 중간 결과는 임시 파일이나 파이프로 전달될 수 있어 현재 디렉터리에 반드시 남지는 않는다.

빌드 성공은 실행 성공의 필요 조건일 수 있지만 충분 조건은 아니다. 실행 환경의 문제, 실행 중 실패, 기대와 다른 출력은 별도로 확인해야 한다. 경고가 없다는 사실도 논리적 정확성의 증명은 아니다.

## 내부 동작

1. **[C 표준] 번역 관점:** 전처리 지시문 처리 이후 선언과 문장의 문법 및 제약 조건을 검사한다. 번역 단위와 외부 함수의 연결 관계가 프로그램 형성에 관여한다.
2. **[GCC/Linux 구현] 도구 관점:** GCC는 대상 CPU용 어셈블리 및 오브젝트를 만들고, 링커가 오브젝트와 필요한 시작 코드·라이브러리를 연결하도록 한다. 최적화나 도구 버전에 따라 실제 중간 형태는 달라질 수 있다.
3. **[GCC/Linux 구현] OS 관점:** 셸이 `./hello` 실행을 요청하면 Linux 커널은 일반적으로 ELF 형식의 실행 파일을 읽어 새 프로그램 이미지를 구성한다. 동적 링크된 실행 파일이라면 지정된 동적 로더가 공유 라이브러리 로딩과 필요한 심볼 재배치 등을 담당한다. 정적 링크된 경우 경로가 다르다.
4. **[GCC/Linux 구현] CPU·메모리 관점:** 코드와 데이터가 프로세스의 가상 주소 공간에 배치된다. CPU는 시작 코드부터 기계 명령을 실행하며 런타임의 준비를 거쳐 `main`에 도달한다. 실행 파일 첫 바이트가 곧 `main`의 첫 명령이라는 뜻은 아니다.
5. **[C 표준] 종료 관점:** 초기 `main`에서 반환하면 `exit` 호출에 대응하는 정상 종료 절차를 거친다. **[GCC/Linux 구현]** 셸은 프로세스 종료 결과를 받아 `$?`로 노출한다.
