# Step 0-1. 전체 컴파일 과정 개요

기준: C17, 호스트 환경(hosted environment). 명령은 GCC가 설치된 Linux 셸에서 실행한다. C 문법을 외우기 전에 소스가 어떤 산출물로 바뀌는지 지도를 만든다.

## 1. 학습 목표

- 소스 파일, 전처리 결과, 어셈블리, 목적 파일, 실행 파일을 구별한다.
- GCC의 네 단계 파이프라인과 ISO C의 추상적 번역 단계를 구별한다.
- `-E`, `-S`, `-c`, `-o`의 역할을 설명하고 산출물을 관찰한다.
- 빌드와 실행을 구별하고 실패한 명령 이후의 결과를 성공으로 오해하지 않는다.

## 2. 선수 지식

- 터미널에서 현재 디렉터리를 확인하고 텍스트 파일을 편집할 수 있으면 된다.
- 함수나 메모리 구조를 미리 알 필요는 없다. 아래 코드는 관찰용 최소 입력이다.
- `gcc --version`으로 GCC 설치를 확인한다. 이후 명령의 시작 위치는 각 실습 README에 명시한다.

## 3. 핵심 개념

### 프로그램을 만드는 과정과 실행하는 과정

소스(source)는 사람이 작성한 C 텍스트다. 번역(translation)은 이 텍스트를 실행 가능한 프로그램으로 만드는 과정이다. 빌드(build)는 보통 번역과 링크를 포함하는 작업을 뜻하지만 ISO C의 특정 단계 이름은 아니다. 실행(execution)은 만들어진 프로그램의 동작이며, 빌드 명령을 실행했다는 사실과 구별해야 한다.

**[GCC/Linux 구현]** 다음은 학습용 실용 파이프라인이다. `gcc`는 C 번역만 하는 단일 도구의 이름으로 쓰이기도 하지만, 명령줄에서는 전처리기, 컴파일러, 어셈블러, 링커를 조정하는 드라이버(driver)다.

```text
hello.c --전처리--> hello.i --컴파일--> hello.s --어셈블--> hello.o --링크--> hello
```

| 산출물 | 의미 | 그 자체를 프로그램으로 실행하는가? |
|---|---|---|
| `.c` | C 소스 텍스트 | 아니오 |
| `.i` | 전처리된 C 입력 | 아니오 |
| `.s` | 대상 CPU용 어셈블리 텍스트 | 아니오 |
| `.o` | 기계 코드와 심볼·재배치 정보 등을 담은 목적 파일(object file) | 보통 아니오 |
| `hello` | 링크된 실행 파일 | 지원되는 실행 환경에서 실행 |

목적 파일은 단순한 기계 명령 바이트의 나열이 아니다. 아직 정해지지 않은 주소 등을 처리하기 위한 정보도 포함할 수 있다. 링크는 목적 파일과 필요한 라이브러리 등을 연결하는 과정이다. 모든 라이브러리의 코드가 항상 실행 파일 안에 복사되는 것은 아니다.

**[C 표준]** 표준은 `.i`, `.s`, `.o`, ELF 형식이나 `gcc` 명령을 요구하지 않는다. 확장자와 파일 형식은 구현의 약속이다. 구현은 여러 번역 단계를 합쳐 수행할 수 있으며, 각 단계마다 실제 파일을 만들 의무도 없다.

## 4. 문법 또는 명령

아래는 `hello.c`가 있는 디렉터리에서 실행하는 명령이다. `-std=c17`은 C17 모드를 선택한다. 경고 옵션은 잘못된 코드를 찾는 데 도움을 주지만, 경고가 없다고 모든 표준 위반이 없다는 증명은 아니다.

```sh
gcc -std=c17 -Wall -Wextra -pedantic -E hello.c -o hello.i
gcc -std=c17 -Wall -Wextra -pedantic -S hello.i -o hello.s
gcc -c hello.s -o hello.o
gcc hello.o -o hello
./hello
```

- `-E`: 전처리 후 멈춘다. `-o`가 없으면 결과를 보통 표준 출력으로 보낸다.
- `-S`: 어셈블리 생성 후 멈춘다. GCC는 `.i`를 전처리된 C 입력으로 취급한다.
- `-c`: 어셈블까지 수행하고 링크는 하지 않는다. `.s` 입력이면 C 전처리·컴파일은 필요 없다.
- `-o 파일명`: 출력 이름을 정한다. 단계 선택 옵션이 아니다.
- `./hello`: 현재 디렉터리의 실행 파일을 실행한다. GCC 옵션이 아닌 셸 명령이다.

중간 산출물을 직접 남기지 않는 전체 빌드는 다음과 같다.

```sh
gcc -std=c17 -Wall -Wextra -pedantic hello.c -o hello && ./hello
```

`&&`는 앞 명령이 성공한 경우에만 뒤 명령을 실행하는 셸 연산자다. 예전 실행 파일이 남아 있어도 빌드 실패 뒤 무심코 실행하는 일을 줄인다.

## 5. 최소 코드 예제

관찰용 `hello.c`의 전체 내용이다. 실습 문제의 완성 답안 파일은 제공하지 않는다.

```c
#include <stdio.h>

int main(void)
{
    puts("Hello, C17!");
    return 0;
}
```

**[C 표준]** 표준 라이브러리를 사용할 수 있는 호스트 환경을 전제로 한 이식 가능한 C17 프로그램이다. 파일 확장자는 GCC의 입력 판별을 위한 관례다.

## 6. 코드 해석

| 줄 | 해석 |
|---|---|
| 1 | `<stdio.h>`라는 표준 헤더를 포함한다. `puts`를 사용할 수 있는 선언 등을 제공한다. |
| 2 | 빈 줄은 가독성을 위한 것이며 동작을 추가하지 않는다. |
| 3 | 인수를 받지 않고 `int`를 반환하는 `main`을 정의하기 시작한다. |
| 4 | 함수 본문의 시작이다. |
| 5 | 문자열을 표준 출력에 쓰고 줄바꿈을 덧붙이는 `puts`를 호출한다. |
| 6 | `main`에서 0을 반환하여 호스트 환경에 성공 종료를 알린다. |
| 7 | 함수 본문의 끝이다. |

정상적인 터미널 출력 환경에서는 `Hello, C17!`과 줄바꿈이 보인다. 헤더를 포함하는 것 자체는 화면에 아무것도 출력하지 않는다.

## 7. 내부 동작

### ISO C의 추상적 번역 단계

**[C 표준]** C17 5.1.1.2의 개념적 순서는 다음과 같다. 아래 여덟 단계를 GCC의 네 명령과 일대일로 대응시키면 안 된다.

1. 물리적 소스 문자를 소스 문자 집합에 대응시키고, C17에 존재하는 삼중자(trigraph)를 치환한다.
2. 역슬래시 바로 뒤의 줄바꿈을 제거하여 물리적 줄을 이어 붙인다.
3. 전처리 토큰과 공백 문자로 나누고, 각 주석을 공백 하나로 바꾼다.
4. 전처리 지시문을 처리하고 매크로를 확장한다. 포함한 파일에도 1~4단계 처리를 재귀적으로 적용하며, 처리한 지시문은 제거한다.
5. 문자 상수와 문자열 리터럴의 문자 및 이스케이프 시퀀스를 실행 문자 집합에 맞게 변환한다.
6. 인접한 문자열 리터럴을 연결한다.
7. 전처리 토큰을 언어 토큰으로 바꾸고 문법·의미 분석 및 번역을 수행한다.
8. 외부 객체·함수 참조를 해결하고 필요한 라이브러리 구성 요소 등을 연결하여 프로그램 이미지를 만든다.

이 순서는 관찰 가능한 의미를 규정하는 모델이다. 예를 들어 7단계가 반드시 `.s`를 디스크에 써야 한다는 뜻은 아니다. 전처리를 거친 한 소스의 결과를 번역 단위(translation unit)라고 한다. 헤더와의 관계는 다음 Step에서 살펴본다.

### 도구·OS·CPU 관점

**[GCC/Linux 구현]** 전처리 결과와 어셈블리는 읽을 수 있는 텍스트지만, 목적 파일과 실행 파일은 일반적으로 바이너리 컨테이너다. Linux에서는 보통 ELF를 사용하나 이는 C17의 요구가 아니다. 기본 전체 빌드는 중간 파일을 보존하지 않을 수 있다.

실행 시에는 OS의 로더와, 동적 링크된 경우 동적 링커가 관여한다. CPU는 준비된 프로그램의 기계 명령을 수행한다. CPU가 `#include`를 읽거나 실행 중에 C 소스를 자동 번역하는 구조가 아니다. 시작 코드가 `main` 호출을 준비하므로 `main`이 실행 파일의 첫 기계 명령이라고 단정해서도 안 된다.

## 8. 자주 하는 실수

- **`.o`를 실행 파일로 생각한다.** `-c`는 링크를 하지 않는다.
- **`-o`를 링크 옵션으로만 외운다.** `-E -o hello.i`처럼 다른 단계의 출력에도 사용한다.
- **빌드와 실행을 혼동한다.** 성공한 `gcc`가 아무 메시지도 출력하지 않는 것은 정상일 수 있다.
- **기본 빌드 뒤 `.i`가 없으니 전처리를 안 했다고 생각한다.** 중간 파일 보존과 단계 수행은 다르다.
- **오류가 나도 다음 명령을 계속 실행한다.** 먼저 실패한 명령의 오류를 읽는다. 남아 있던 옛 산출물은 이번 성공의 증거가 아니다.
- **ISO C가 GCC의 네 단계를 규정한다고 말한다.** 추상적 번역 모델과 구체적 도구 구성을 구별한다.

## 9. 필수 실습

### 실습 A. 같은 소스의 다섯 가지 모습

- **목적:** 소스에서 실행까지 산출물의 역할을 구별한다.
- **해야 할 일:** [실습 안내](../../exercises/00-compilation/0-1/README.md)에 따라 예제를 직접 입력하고, 출력 문구를 자신만의 ASCII 문구로 바꾼다. 각 중간 파일을 만들고 이름·생성 명령·텍스트 여부·역할을 표로 기록한다. 마지막으로 전체 빌드 결과와 단계별 빌드 결과의 출력을 비교한다.
- **사용할 개념:** 전처리, 컴파일, 어셈블, 링크, `-E`, `-S`, `-c`, `-o`, 실행.
- **예상 관찰 결과:** `.i`에는 포함된 헤더의 내용이 보이고 `.s`는 C 소스와 다르다. `.o` 생성만으로는 프로그램 출력이 나타나지 않는다. 링크한 프로그램을 실행하면 변경한 문구가 보인다.
- **확인 포인트:** 각 명령이 멈추는 지점을 설명했는가? 파일 크기나 어셈블리 내용이 다른 환경에서도 같아야 한다고 가정하지 않았는가? 모든 빌드 명령의 성공을 확인했는가?

## 10. 추가 실습

- ★ **이름 바꾸기:** `-o`로 실행 파일 이름만 바꿔 빌드하고 실행한다. 이름 변경이 C 소스의 의미를 바꾸는지 설명한다.
- ★★ **드라이버 관찰:** `gcc -### -std=c17 hello.c -o hello`의 표준 오류 출력을 읽고 내부 도구 호출을 찾는다. `-###`는 명령을 보여 주되 실행하지 않는 GCC 옵션이다. 경로나 도구 이름 자체를 암기하지 않는다.

## 11. 확인 문제

1. GCC 실용 파이프라인의 네 단계와 대표 산출물은 무엇인가?
2. ISO C가 `.s` 파일 생성을 요구하는가?
3. `gcc -c hello.c -o hello.o` 성공 직후 `Hello, C17!`이 출력되지 않는 이유는?
4. `#include <stdio.h>`는 `puts`의 기계 코드를 소스에 복사하는가?
5. `gcc` 명령이 실패했는데 `./hello`는 실행될 수 있는 이유는?

<details>
<summary>정답과 해설 펼치기</summary>

1. 전처리 `.i`, 컴파일 `.s`, 어셈블 `.o`, 링크 실행 파일이다. 모든 파일을 항상 디스크에 보존한다는 뜻은 아니다.
2. 아니다. 표준은 추상적 번역의 의미를 규정하며 특정 중간 파일 형식을 요구하지 않는다.
3. 목적 파일까지만 만들었고 링크·프로그램 실행을 하지 않았기 때문이다.
4. 아니다. 표준 헤더가 제공하는 선언 등을 사용할 수 있게 한다. 필요한 라이브러리의 연결은 별개의 문제다.
5. 이전에 성공한 빌드의 실행 파일이 남아 있을 수 있다. 이번 빌드가 성공한 증거가 아니며 `&&`로 실행을 연결하면 이 혼동을 줄일 수 있다.

## 12. 핵심 정리

- GCC의 네 단계는 실용 지도이며 ISO C의 여덟 추상 단계와 동일한 분류가 아니다.
- `.i`와 `.s`는 텍스트, `.o`는 목적 파일이며 링크된 실행 파일과 다르다.
- C17은 소스의 의미를 규정하지만 GCC 옵션, ELF, Linux 로더는 규정하지 않는다.
- 빌드 성공과 실행 결과를 각각 확인한다.
