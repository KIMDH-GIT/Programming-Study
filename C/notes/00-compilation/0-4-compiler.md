# Step 0-4. 컴파일러와 `.s` 파일: `gcc -S`

## 1. 학습 목표

- 전처리와 좁은 의미의 컴파일을 구분한다.
- `gcc -S`로 어셈블리 소스를 만들고 생성 단계의 끝을 설명한다.
- C 코드와 어셈블리가 반드시 한 줄씩 대응하지 않는 이유를 설명한다.
- C 표준의 의미 규칙과 특정 CPU용 명령어를 구별한다.

## 2. 선수 지식

- Step 0-1의 전처리 → 컴파일 → 어셈블 → 링크 흐름
- Step 0-2의 `.c`, `.h`와 Step 0-3의 `gcc -E`, 전처리 결과 `.i`
- 터미널에서 작업 디렉터리로 이동하고 텍스트 파일을 저장하는 방법

명령은 GCC가 설치된 GNU/Linux 셸에서 실행한다. 예제의 C 언어 기능은 C17에서 사용할 수 있다. 어셈블리 문법을 외우거나 직접 작성할 필요는 없다.

## 3. 핵심 개념

### 컴파일이라는 말의 두 범위

일상적으로는 소스에서 실행 파일까지 만드는 전체 작업을 “컴파일”이라고 부르기도 한다. 여기서는 전처리된 C를 분석하여 어셈블리 소스를 생성하는 **좁은 의미의 컴파일**에 집중한다. GCC의 `gcc` 명령은 여러 도구를 연결하는 **컴파일러 드라이버**이므로 명령 이름만 보고 어디까지 진행했는지 판단하면 안 된다.

**[C 표준]** C는 식, 문장, 형식, 함수 호출 등의 의미와 번역 과정의 요구 사항을 규정한다. 번역 단위(translation unit)는 전처리를 거쳐 남은 소스이며, 포함된 헤더의 내용도 반영된다. 표준의 개념적 번역 단계가 실제 도구의 프로세스나 중간 파일과 일대일로 대응할 필요는 없다. `.s` 파일을 반드시 디스크에 만들라는 요구도 없다.

**[GCC/Linux 구현]** `gcc -S hello.c`는 필요한 전처리와 컴파일을 수행한 뒤 어셈블 전에 멈춘다. 출력인 `hello.s`는 대상 CPU와 어셈블러 문법에 맞춘 **텍스트 형태의 어셈블리 소스**다. 이미 전처리된 `hello.i`를 입력하면 GCC는 확장자를 보고 전처리가 끝난 C 소스로 취급한다.

### 컴파일러가 판단하는 것

컴파일러는 토큰을 문법 구조로 묶고 선언 및 형식 관계를 검사한 뒤 프로그램의 의미를 기계에서 수행할 연산으로 바꾼다. 이름을 잘못 썼거나 문법이 깨진 경우 이 과정에서 진단이 발생할 수 있다. 컴파일 성공은 모든 버그의 부재나 외부 함수 정의의 존재를 보증하지 않는다. 외부 정의 연결은 뒤의 링크 단계에서 필요할 수 있다.

**[C 표준]** 관찰 가능한 동작을 보존하는 범위에서 구현은 연산을 바꾸거나 없앨 수 있다. 이를 흔히 **as-if 규칙**이라고 설명한다. “작성한 각 줄이 반드시 명령어 하나가 된다”는 규칙은 없다.

**[GCC/Linux 구현]** 최적화 옵션, GCC 버전, 대상 CPU, 배포판의 기본 보안 옵션에 따라 `.s`의 내용이 달라진다. `-O0`는 관찰용으로 유용하지만 모든 내부 변환을 끄거나 원문과 일대일 대응을 보장하지 않는다.

## 4. 문법 또는 명령

다음 명령은 `hello.c`를 저장한 디렉터리에서 실행한다.

```sh
gcc --version
gcc -dumpmachine
gcc -std=c17 -Wall -Wextra -Wpedantic -O0 -S hello.c -o hello.s
less hello.s
```

`less`에서는 방향키로 이동하고 `q`로 나온다. 텍스트 편집기로 열어도 된다.

| 요소 | 의미 |
|---|---|
| `-std=c17` | C17 언어 모드를 선택한다. |
| `-Wall -Wextra -Wpedantic` | 유용한 진단을 요청한다. 모든 오류 검출을 보장하지 않는다. |
| `-O0` | 최적화 수준을 지정한다. 마지막 문자는 숫자 0이다. |
| `-S` | 컴파일 후 멈추고 어셈블리 소스를 출력한다. 대문자 S다. |
| `-o hello.s` | 출력 경로를 지정한다. 출력 형식은 확장자가 아니라 단계 옵션이 결정한다. |

전처리 결과에서 시작하는 경로도 확인할 수 있다.

```sh
gcc -std=c17 -E hello.c -o hello.i
gcc -std=c17 -Wall -Wextra -Wpedantic -O0 -S hello.i -o hello-from-i.s
```

두 경로가 같은 프로그램 의미를 번역한다는 것이 핵심이다. 파일 경로 등의 메타데이터 때문에 출력 전체가 바이트 단위로 같아야 한다고 가정하지 않는다.

## 5. 최소 코드 예제

`hello.c`:

```c
#include <stdio.h>

int main(void)
{
    puts("compiler stage");
    return 0;
}
```

**[C 표준]** 표준 입출력 함수를 쓰는 호스트 환경(hosted environment)의 이식 가능한 예제다. 실행되면 `puts`가 문자열과 줄바꿈을 출력한다. 이 Step에서는 실행하지 않고 번역 결과만 관찰한다. 정상 출력이 가능한 환경을 가정하며 입출력 실패 처리는 이번 관찰의 범위 밖이다.

## 6. 코드 해석

| 줄 | 해석 |
|---|---|
| 1 | 전처리 지시문이다. `<stdio.h>`의 선언을 제공받으며 라이브러리 구현을 복사하는 명령이 아니다. |
| 2 | 빈 줄로, 읽기 쉽게 구분한다. |
| 3 | 인수가 없는 `main` 함수를 정의한다. 반환 형식은 `int`다. |
| 4 | 함수 본문이 시작된다. |
| 5 | 표준 함수 `puts`를 호출한다. 문자열 끝의 널 문자와 출력되는 줄바꿈은 서로 다른 것이다. |
| 6 | 호스트 환경에 성공 종료를 뜻하는 값을 반환한다. 아직 이 줄이 실행된 것은 아니다. |
| 7 | 함수 본문이 끝난다. |

**[GCC/Linux 구현: GNU/Linux 관찰]** `.s`에서 `main`이라는 이름, 문자열 데이터, `puts`에 대한 참조를 찾아본다. ELF 대상 GCC 출력에서 `.text`, `.globl`, `.string` 같은 어셈블러 지시문이 보일 수 있다. 지시문은 모두 CPU가 실행하는 명령어가 아니다.

**[GCC/Linux 구현: x86-64 GNU/Linux 관찰]** 함수 호출이 `call puts@PLT`처럼 나타날 수 있다. 다른 대상에서는 호출 명령의 철자와 형식이 다르며 x86-64에서도 옵션에 따라 간접 호출 등으로 달라질 수 있다. 지금은 `@PLT`의 구조보다 외부 함수 호출이 표현된다는 점만 확인한다.

## 7. 내부 동작

개념적으로 프런트엔드는 C의 문법과 의미를 분석하고, 중간 표현(IR, intermediate representation)에서 변환을 수행하며, 백엔드는 대상에 맞는 명령 선택과 레지스터 배치 등을 수행한다. 실제 GCC 내부 패스는 이보다 복잡하며 고정된 세 번의 처리로 이해하면 안 된다.

- **C 관점:** 소스가 뜻하는 동작과 형식 관계를 정한다.
- **컴파일러 관점 [GCC/Linux 구현]:** IR을 거쳐 대상용 어셈블리와 지시문을 출력한다.
- **CPU 관점 [GCC/Linux 구현]:** 대상의 명령어 집합(ISA)이 생성 가능한 기계 연산을 제한한다. CPU는 `.s`의 텍스트를 직접 실행하지 않는다.
- **메모리/OS 관점 [GCC/Linux 구현]:** 문자열을 어느 영역에 둘지 같은 정보가 표현될 수 있지만, 아직 이 프로그램을 실행할 프로세스의 메모리가 구성된 것은 아니다. 컴파일러 프로세스의 실행과 학습 대상 프로그램의 실행은 다르다.

다음 단계의 어셈블러가 명령어를 기계어로 인코딩하고 목적 파일을 만든다. 따라서 `.s`가 존재한다는 사실만으로 실행 파일이 생겼다고 말할 수 없다.

## 8. 자주 하는 실수

- `-S`를 `-s`로 쓰기: GCC의 소문자 `-s`는 링크 시 심벌 정보 제거와 관련된 다른 옵션이다.
- `gcc -S hello.c -o hello`의 결과를 실행 파일로 생각하기: 이름이 `hello`여도 어셈블리 텍스트다.
- `.s`를 `./hello.s`로 실행하기: 텍스트를 기계 실행 파일처럼 실행할 수 없다. 실행 권한을 추가해도 해결되지 않는다.
- `.s`가 예시와 다르면 실패로 판단하기: CPU, 버전, 기본 옵션 차이를 먼저 확인한다.
- 헤더가 포함되면 `puts`의 기계어도 `.s`에 들어 있다고 생각하기: 선언을 이용한 호출 생성과 정의 연결은 다르다.

## 9. 필수 실습

### 실습 A. 컴파일 단계의 경계 확인

- **목적:** `.c` 또는 `.i`가 `.s`로 바뀌는 단계와 실행 단계를 구별한다.
- **해야 할 일:** 예제를 직접 입력하고 4절의 두 경로를 실행한다. `hello.s`와 `hello-from-i.s`에서 함수 이름, 문자열, 외부 함수 참조를 각각 찾는다. 이번 명령이 `.o`나 실행 파일을 새로 만들었는지도 확인한다.
- **사용할 개념:** 번역 단위, 전처리, `-S`, 어셈블리 지시문, 대상 CPU
- **예상 관찰 결과:** 읽을 수 있는 어셈블리 파일이 만들어지지만 프로그램의 문자열이 실행 출력으로 나타나지 않는다. 문자열은 파일 안의 데이터로 보인다.
- **확인 포인트:** “컴파일러가 실행됐다”와 “내 프로그램이 실행됐다”를 구분하는 문장을 쓴다. 두 파일에서 철자가 다른 줄보다 의미상 대응하는 부분을 설명한다.

## 10. 추가 실습

- **★ 기초:** 문자열을 바꾸고 다른 이름의 `.s`를 만든다. 문자열 데이터가 바뀌는 위치를 찾는다.
- **★★ 확장:** 같은 소스에 `-O2`를 사용하여 `hello-O2.s`를 만들고 `-O0` 결과와 비교한다. 줄 수나 특정 명령어 개수는 정답 기준으로 삼지 않는다. 관찰 가능한 출력 의미가 유지되어야 한다는 기준을 적는다.

## 11. 확인 문제

1. `gcc -S hello.c`는 전처리도 하는가? 어디서 멈추는가?
2. `.s` 파일이 생성되면 CPU가 그 텍스트를 직접 실행할 수 있는가?
3. `.s`에 있는 `.globl` 같은 지시문도 모두 CPU 명령어인가?
4. C의 한 줄이 어셈블리 한 줄과 대응하지 않는 이유는 무엇인가?
5. `.i`와 `.s`는 둘 다 텍스트인데 어떤 차이가 있는가?

<details>
<summary>정답과 해설 펼치기</summary>

1. `.c` 입력에는 전처리와 컴파일을 수행하고 어셈블 전에 멈춘다.
2. 아니다. 어셈블과 링크 등 후속 작업이 필요하다.
3. 아니다. 지시문은 심벌 속성이나 데이터 배치 등 어셈블러의 처리를 지시한다.
4. C는 추상적인 동작을 표현하며 대상 명령어의 세분화 정도가 다르다. 최적화도 동작을 보존하며 연산을 합치거나 없앨 수 있다.
5. `.i`는 전처리된 C이며 `.s`는 특정 대상용 어셈블리 소스다. 읽을 수 있다는 공통점만으로 같은 언어는 아니다.

## 12. 핵심 정리

- **[C 표준]** C의 의미와 번역 요구 사항은 특정 중간 파일이나 ISA에 종속되지 않는다.
- **[GCC/Linux 구현]** `gcc -S`는 어셈블리 소스를 만들고 어셈블 전에 멈춘다.
- 어셈블리에는 명령어뿐 아니라 데이터, 레이블, 지시문도 있다.
- `.s`는 실행 파일이 아니며 컴파일 성공만으로 링크나 실행 성공을 보장하지 않는다.
