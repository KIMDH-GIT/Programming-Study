# Step 0-2. C 소스 `.c`와 헤더 `.h`

기준: C17의 호스트 환경. `.c`와 `.h`는 역할을 나타내는 관례이며, 번역 단위의 경계는 파일 개수만 세어 결정하지 않는다.

## 1. 학습 목표

- 소스 파일, 헤더, 전처리 번역 단위, 번역 단위를 구별한다.
- 선언(declaration)과 정의(definition)의 차이를 간단한 함수 예로 설명한다.
- `#include "..."`와 `#include <...>`의 검색 규칙을 표준과 GCC 관점으로 나누어 설명한다.
- 표준 전처리 지시문으로 include guard를 만들고 적용 범위를 설명한다.

## 2. 선수 지식

- [Step 0-1](0-1-compilation-overview.md)의 GCC 파이프라인과 빌드·실행 구분.
- 편집기로 파일을 만들고 해당 디렉터리에서 GCC를 실행하는 방법.
- 함수 본문 `{ ... }`과 함수 선언 끝의 `;`가 다르다는 점만 우선 읽으면 된다. 함수 문법 전반은 이 Step의 범위가 아니다.

## 3. 핵심 개념

### 소스와 헤더의 역할

**[GCC/Linux 구현]** `.c` 파일은 보통 함수 정의 등 구현을 작성하고 개별 컴파일 입력으로 준다. `.h` 파일에는 여러 소스가 공유할 함수 선언, 타입 선언, 매크로 정의 등을 둔다. 헤더는 보통 다른 소스에서 포함하며 **독립 번역 단위로 직접 컴파일하지 않는다.** GCC가 헤더 입력으로 미리 컴파일된 헤더를 만드는 기능은 별도 기능이지 일반적인 프로그램 빌드 절차가 아니다.

**[C 표준]** 확장자는 지정하지 않는다. 하나의 소스 파일에 `#include`로 포함한 모든 헤더·소스 파일을 더하고 조건부 포함으로 제외한 부분을 뺀 것이 전처리 번역 단위(preprocessing translation unit)다. 전처리 후의 결과가 번역 단위(translation unit)다. 헤더 둘을 포함하는 소스 하나가 자동으로 세 번역 단위가 되지 않는다.

서로 다른 `main.c`와 `message.c`를 각각 컴파일하면 각자 번역 단위를 이룬다. 둘이 같은 헤더를 포함해도 하나로 합쳐지는 것은 아니다. 한 소스의 매크로 정의가 다른 소스의 전처리 상태로 자동 전파되지도 않는다.

### 선언과 정의

선언은 이름과 타입 등의 정보를 알린다. 정의는 함수의 본문이나 객체의 저장 공간을 제공하는 선언이다. 따라서 정의도 선언의 일종이다.

- `int answer(void);`는 인수 없이 `int`를 반환하는 함수의 선언이며 본문이 없다.
- `int answer(void) { return 42; }`는 그 함수의 정의다.

공유 함수 선언을 헤더에 두고, 호출하는 `.c`와 정의하는 `.c`가 모두 그 헤더를 포함하면 컴파일러가 선언과 사용·정의의 타입 일치를 확인하는 데 도움이 된다. 선언만 포함한다고 함수 구현이 생기는 것은 아니다. 사용하는 외부 함수의 정의는 다른 번역 단위나 라이브러리에서 제공되어 연결되어야 한다.

모든 정의를 헤더에서 금지한다는 규칙도 정확하지 않다. 매크로와 타입 정의는 흔히 헤더에 둔다. 다만 이 단계에서는 외부 연결을 갖는 일반 함수 본문이나 `int count = 0;` 같은 객체 정의를 헤더에 두지 않는다. 여러 번역 단위에 중복 정의가 생길 수 있다. `static`·`inline` 같은 별도 설계는 여기서 다루지 않는다.

### include 검색과 재포함 방지

**[C 표준]** `<...>` 형식은 구현 정의의 장소에서 헤더를 검색한다. `"..."` 형식은 구현 정의의 방식으로 소스 파일을 검색하며, 지원되지 않거나 검색에 실패하면 `<...>` 형식으로 다시 처리한다. 표준이 "현재 작업 디렉터리부터 검색"이라고 지정하지는 않는다. 표준 헤더도 반드시 일반 디스크 파일일 필요는 없다.

**[GCC/Linux 구현]** `"..."`는 먼저 해당 지시문을 가진 파일의 디렉터리, 이어 `-iquote` 디렉터리, 그 뒤 `<...>`에 적용되는 검색 경로를 사용한다. `<...>`는 `-I`로 추가한 디렉터리와 구성된 시스템 검색 경로 등을 사용한다. 정확한 시스템 경로는 GCC 설치와 타깃에 따라 다르다. 셸의 현재 디렉터리와 포함 지시문이 있는 파일의 디렉터리를 혼동하지 않는다.

include guard는 매크로가 아직 정의되지 않은 경우에만 헤더 본문을 처리하게 한다. 동일 번역 단위 안에서 반복 포함을 막는다. 서로 다른 번역 단위에 생기는 중복 외부 정의를 막아 주지는 않는다.

## 4. 문법 또는 명령

```c
#include <stdio.h>
#include "message.h"
```

표준 헤더는 보통 `<...>`, 프로젝트 헤더는 보통 `"..."`로 쓴다. 이것은 적절한 관례이지 두 형태가 파일 종류를 엄격히 분류한다는 뜻은 아니다. 지시문 끝에 세미콜론을 붙이지 않는다.

`main.c`와 `message.h`가 같은 디렉터리에 있을 때:

```sh
gcc -std=c17 -Wall -Wextra -pedantic main.c -o main && ./main
gcc -std=c17 -E main.c -o main.i
```

헤더를 `include/` 디렉터리로 옮긴 경우에는 검색 경로를 추가할 수 있다.

```sh
gcc -std=c17 -Wall -Wextra -pedantic -I include main.c -o main && ./main
```

`-I`는 GCC 옵션이지 C 문법이 아니다. 아래 최소 예제에는 별도 함수 구현이 없으므로 `.h`를 빌드 입력으로 나열하지 않는다.

## 5. 최소 코드 예제

관찰용 `message.h`:

```c
#ifndef STUDY_MESSAGE_H
#define STUDY_MESSAGE_H

#define COURSE_MESSAGE "C17 headers"

#endif
```

관찰용 `main.c`:

```c
#include <stdio.h>
#include "message.h"

int main(void)
{
    puts(COURSE_MESSAGE);
    return 0;
}
```

**[C 표준]** 여기서 사용한 include guard와 객체형 매크로는 표준 기능이다. 예약 식별자와 충돌하지 않도록 guard 이름에 밑줄로 시작하는 이름을 쓰지 않았다. 두 파일은 헤더 공유 관찰용이며 필수 실습의 함수 분리 답안은 아니다.

## 6. 코드 해석

| 파일·줄 | 해석 |
|---|---|
| `message.h` 1 | `STUDY_MESSAGE_H`가 정의되지 않았다면 뒤의 그룹을 처리한다. |
| `message.h` 2 | guard 매크로를 정의하여 이후 재포함 때 같은 그룹을 제외한다. |
| `message.h` 3, 5 | 읽기 편하게 하는 빈 줄이다. |
| `message.h` 4 | `COURSE_MESSAGE`를 문자열 리터럴로 치환하는 매크로를 정의한다. 변수를 만드는 것이 아니다. |
| `message.h` 6 | 조건부 포함 그룹을 닫는다. |
| `main.c` 1 | `puts`를 사용할 수 있도록 표준 헤더를 포함한다. |
| `main.c` 2 | 프로젝트 헤더를 포함하여 매크로를 사용할 수 있게 한다. |
| `main.c` 3 | 빈 줄이다. |
| `main.c` 4~5 | `main` 함수 정의와 본문을 시작한다. |
| `main.c` 6 | 전처리 후에는 문자열 리터럴을 인수로 `puts`를 호출하는 형태가 된다. |
| `main.c` 7~8 | 성공 종료 값을 반환하고 본문을 닫는다. |

## 7. 내부 동작

**[C 표준]** include는 실행 시 파일을 읽는 함수 호출이 아니다. 전처리 시 지정한 헤더·소스 파일의 내용으로 지시문을 대체하고 그 내용도 전처리한다. 따라서 guard의 상태는 프로그램 메모리의 런타임 플래그가 아니라 전처리 중의 매크로 정의 상태다.

**[GCC/Linux 구현]** 헤더가 바뀌면 그것을 포함하는 각 `.c`를 다시 컴파일해야 변경이 반영된다. 빌드 도구가 의존성을 추적할 수 있지만 여기서는 GCC를 직접 호출하므로 필요한 소스를 직접 다시 빌드한다. 헤더 수정만으로 기존 실행 파일이 바뀌지 않는다.

함수 선언은 컴파일러가 호출의 타입 등을 검사하는 데 쓰인다. 일반적인 링커는 C 헤더를 다시 읽어 함수 원형의 일치를 검증하는 도구가 아니다. 선언과 정의가 서로 다른 번역 단위에서 잘못 맞아도 평범한 링크만으로 모두 잡아 준다고 기대해서는 안 된다. 공통 헤더를 양쪽에서 포함하는 이유다.

CPU와 OS는 `.h`라는 파일 역할을 C 의미로 이해하지 않는다. 런타임에 필요한 코드·데이터는 빌드 산출물에 반영되며, 보통 실행할 때 원래 헤더를 다시 찾을 필요는 없다.

## 8. 자주 하는 실수

- **`gcc main.c message.h -o main`을 일반 빌드로 사용한다.** 헤더는 `main.c`가 포함한다. 별도 구현이 있다면 그 `.c`를 빌드 입력에 추가한다.
- **`#include "message.c"`로 소스를 합친다.** 기술적으로 가능하지만 일반적인 분리 컴파일 구조가 아니다. 같은 구현을 별도 입력에도 넣으면 중복 정의가 생길 수 있다.
- **guard만 있으면 함수 본문도 어디에나 넣어도 된다고 생각한다.** guard는 한 번역 단위 내부 재포함만 막는다.
- **여러 헤더에서 같은 guard 이름을 쓴다.** 먼저 포함한 헤더가 뒤 헤더의 내용을 뜻하지 않게 제외할 수 있다.
- **헤더 선언만으로 링크가 완료된다고 생각한다.** 실제로 사용하는 함수의 정의도 제공해야 한다.
- **`#pragma once`를 ISO C17의 보장이라고 말한다.** GCC 등이 지원하는 방식이지만 여기서는 표준 지시문으로 구성한 guard를 사용한다.

## 9. 필수 실습

### 실습 A. 공유 선언과 구현 파일 분리

- **목적:** 헤더가 계약을 공유하고 `.c`가 구현을 제공한다는 구조를 확인한다.
- **해야 할 일:** [실습 안내](../../exercises/00-compilation/0-2/README.md)에 따라 `status.h`, `status.c`, `main.c`를 직접 만든다. 헤더에는 guard와 인수 없이 `int`를 반환하는 `study_status`의 선언을 둔다. 구현 파일은 헤더를 포함하고 이 함수를 정의하여 0을 반환한다. `main.c`도 헤더를 포함하고 `main`에서 함수 호출 결과를 반환한다. 두 `.c`를 함께 빌드한 뒤, 비교용으로 `main.c`만 빌드해 본다.
- **사용할 개념:** 선언·정의, 헤더 포함, include guard, 두 번역 단위의 연결.
- **예상 관찰 결과:** 두 구현 파일을 포함한 빌드는 성공하고 프로그램은 성공 종료한다. `main.c`만 빌드하면 일반적인 GCC 환경에서 `study_status` 정의를 찾지 못하는 링크 오류가 난다. 오류 문구는 환경별로 다를 수 있다.
- **확인 포인트:** 두 `.c` 모두 같은 헤더를 포함했는가? `.h`를 별도 빌드 입력에 넣지 않았는가? 선언 누락과 정의 누락이 다른 문제임을 설명할 수 있는가?

## 10. 추가 실습

- ★ **두 번 포함:** 최소 예제의 `message.h`를 연속 두 번 포함한 뒤 `gcc -E`로 살펴본다. guard 처리 뒤 본문이 반복 처리되지 않는 이유를 설명한다. 매크로를 똑같이 재정의하는 일은 항상 오류가 나는 것이 아니므로 "오류 없음"만으로 guard 효과를 증명하지 않는다.
- ★★ **검색 경로:** 최소 예제의 헤더를 `include/`로 옮겨 `-I include` 유무를 비교한다. 표준의 보장과 GCC 검색 경로 설정을 나누어 기록한다.

## 12. 핵심 정리

- 헤더는 공유 선언·타입·매크로를 담아 포함하는 파일이며 보통 독립 번역 단위가 아니다.
- 선언을 볼 수 있는 것과 필요한 정의가 링크에 참여하는 것은 별개다.
- include guard는 번역 단위 내부에서만 재포함을 제어한다.
- include 검색의 세부 경로와 `.c`·`.h` 확장자 처리는 구현에 속한다.
