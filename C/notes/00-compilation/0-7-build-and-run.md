# Step 0-7. 전체 빌드와 실행

## 1. 학습 목표

- `gcc hello.c -o hello`가 수행하는 빌드와 `./hello`가 수행하는 실행을 구별한다.
- 한 번에 빌드한 결과와 단계별로 만든 결과의 관계를 설명한다.
- 빌드 결과, 표준 출력, 종료 상태를 각각 확인한다.
- C가 보장하는 내용과 Linux 도구 체인에서 관찰한 내용을 분리한다.

## 2. 선수 지식

Step 0-1~0-6의 소스, 헤더, 전처리, 컴파일, 어셈블, 링크 개념을 사용한다. `.c`, `.i`, `.s`, `.o`가 각기 어떤 단계의 입력이나 출력인지 알고 있으면 된다. 함수 문법을 완전히 익힐 필요는 없다.

실습 환경은 **[GCC/Linux 구현]** GCC와 개발용 표준 라이브러리가 설치된 Linux 셸이다. 명령은 `hello.c`가 있는 디렉터리에서 실행한다. `gcc --version`으로 도구 유무를 먼저 확인한다.

## 3. 핵심 개념

**빌드(build)**는 소스로부터 실행 가능한 결과물을 만드는 작업이다. 여기서는 GCC 드라이버가 전처리, 좁은 의미의 컴파일, 어셈블, 링크를 조정한다. **실행(run)**은 그 결과물을 운영체제에 실행 요청하는 별도 작업이다. GCC는 빌드에 성공했다고 프로그램까지 실행하지 않는다.

**[C 표준]** 번역 단계는 프로그램을 해석하는 논리적 모형이다. 실제로 `.i`, `.s`, `.o` 파일을 디스크에 남기거나 네 개의 별도 프로그램을 실행해야 한다는 규정은 없다. 호스트 환경의 `main`과 표준 입출력 함수의 의미는 규정하지만 `gcc`, 파일 확장자, 실행 파일 이름은 규정하지 않는다.

**[GCC/Linux 구현]** `gcc`는 C 소스뿐 아니라 오브젝트 파일도 입력받는 드라이버다. 단계 중단 옵션 없이 C 파일을 입력하면 보통 링크까지 수행한다. `-o hello`는 최종 출력 이름을 정하며, 실행 명령이 아니다. 기본 중간 결과는 임시 파일이나 파이프로 전달될 수 있어 현재 디렉터리에 반드시 남지는 않는다.

빌드 성공은 실행 성공의 필요 조건일 수 있지만 충분 조건은 아니다. 실행 환경의 문제, 실행 중 실패, 기대와 다른 출력은 별도로 확인해야 한다. 경고가 없다는 사실도 논리적 정확성의 증명은 아니다.

## 4. 문법 또는 명령

다음은 모두 **[GCC/Linux 구현]** 명령이다.

```sh
gcc --version
gcc hello.c -o hello
```

바로 이어서 성공 여부를 확인한다. `$?`는 Linux 셸에서 직전 명령의 종료 상태를 확장하므로 다른 명령을 끼우지 않는다.

```sh
printf 'build status=%s\n' "$?"
```

위 빌드가 성공한 경우에만 다음을 실행한다.

```sh
./hello
printf 'run status=%s\n' "$?"
```

평소에는 아래처럼 성공한 빌드 뒤에서만 실행하게 연결하는 편이 안전하다.

```sh
gcc -std=c17 -Wall -Wextra -pedantic hello.c -o hello && ./hello
```

`&&`는 셸 문법이다. 앞 명령이 성공 상태일 때만 뒤 명령을 실행한다. 이 전체 목록 직후의 `$?`는 실행이 수행되었다면 실행 상태, 빌드에서 멈췄다면 빌드 상태다. 두 상태를 구별해서 기록할 때는 앞의 분리된 절차를 쓴다.

| 옵션/표현 | 의미 |
|---|---|
| `-std=c17` | GCC가 적용할 C 언어 모드 선택 |
| `-Wall -Wextra -pedantic` | 유용한 경고 및 표준 관련 진단 활성화; 모든 오류 검출 보장은 아님 |
| `-o hello` | 이번 호출에서 만들어지는 출력 파일 이름 지정 |
| `./hello` | 현재 디렉터리에 있는 파일을 경로로 지정하여 실행 |
| `-E`, `-S`, `-c` | 각각 전처리, 컴파일, 어셈블 뒤에서 중단 |

단계별 비교는 다음과 같이 한다. 각 줄이 성공한 것을 확인하고 다음 줄로 이동한다.

```sh
gcc -std=c17 -E hello.c -o hello.i
gcc -std=c17 -S hello.i -o hello.s
gcc -c hello.s -o hello.o
gcc hello.o -o hello-staged
./hello-staged
```

## 5. 최소 코드 예제

`hello.c`에 저장한다. 이 코드는 **[C 표준]**의 호스트 환경용 이식 가능한 C 코드다.

```c
#include <stdio.h>
int main(void)
{
    puts("Hello, C!");
    return 0;
}
```

일반적인 정상 표준 출력 환경에서 관찰할 내용은 `Hello, C!` 한 줄이다. 표준 출력 자체의 실패 처리까지 다루는 예제는 아니므로 출력 함수의 반환값을 검사하지 않는다.

## 6. 코드 해석

| 줄 | 해석 |
|---|---|
| 1 | `<stdio.h>`를 포함해 `puts`의 선언을 제공받는다. 라이브러리 구현 코드를 이 줄이 그대로 복사하는 것은 아니다. |
| 2 | 인수를 받지 않고 `int`를 반환하는 `main`을 정의하기 시작한다. |
| 3 | 함수 본문 시작이다. |
| 4 | 문자열을 표준 출력 스트림에 쓰고 줄바꿈을 덧붙이는 표준 함수 `puts`를 호출한다. |
| 5 | 초기 `main` 호출에서 0을 반환하여 성공 종료를 나타낸다. |
| 6 | 함수 본문 끝이다. |

**[C 표준]** `return 0`에 의한 성공 상태가 호스트 환경에 전달되는 구체적 형태는 구현 정의다. **[GCC/Linux 구현]** 이 예제는 셸에서 보통 종료 상태 0으로 관찰된다. 화면의 문자열과 종료 상태는 별개다.

## 7. 내부 동작

1. **[C 표준] 번역 관점:** 전처리 지시문 처리 이후 선언과 문장의 문법 및 제약 조건을 검사한다. 번역 단위와 외부 함수의 연결 관계가 프로그램 형성에 관여한다.
2. **[GCC/Linux 구현] 도구 관점:** GCC는 대상 CPU용 어셈블리 및 오브젝트를 만들고, 링커가 오브젝트와 필요한 시작 코드·라이브러리를 연결하도록 한다. 최적화나 도구 버전에 따라 실제 중간 형태는 달라질 수 있다.
3. **[GCC/Linux 구현] OS 관점:** 셸이 `./hello` 실행을 요청하면 Linux 커널은 일반적으로 ELF 형식의 실행 파일을 읽어 새 프로그램 이미지를 구성한다. 동적 링크된 실행 파일이라면 지정된 동적 로더가 공유 라이브러리 로딩과 필요한 심볼 재배치 등을 담당한다. 정적 링크된 경우 경로가 다르다.
4. **[GCC/Linux 구현] CPU·메모리 관점:** 코드와 데이터가 프로세스의 가상 주소 공간에 배치된다. CPU는 시작 코드부터 기계 명령을 실행하며 런타임의 준비를 거쳐 `main`에 도달한다. 실행 파일 첫 바이트가 곧 `main`의 첫 명령이라는 뜻은 아니다.
5. **[C 표준] 종료 관점:** 초기 `main`에서 반환하면 `exit` 호출에 대응하는 정상 종료 절차를 거친다. **[GCC/Linux 구현]** 셸은 프로세스 종료 결과를 받아 `$?`로 노출한다.

## 8. 자주 하는 실수

- `gcc hello.c -o hello`가 출력 문장까지 실행한다고 생각한다. 빌드와 실행은 별개다.
- `gcc hello.c -o hello.c`로 소스와 같은 출력 이름을 지정한다. GCC가 거부할 수 있지만 도구의 방어에 의존하지 말고 입력과 출력 이름을 분리한다.
- `hello`만 입력한다. **[GCC/Linux 구현]** 셸의 `PATH`에 현재 디렉터리가 없으면 찾지 못한다. 이 실습은 `./hello`를 쓴다.
- 빌드 실패 뒤 기존 `hello`를 실행하고 수정이 반영됐다고 믿는다. `&&`로 연결하고 매번 빌드 상태를 확인한다.
- `ls`를 실행한 뒤 `$?`를 확인한다. 이때는 GCC가 아니라 `ls`의 상태다.
- `.o`에 실행 권한만 주면 실행된다고 생각한다. 재배치 가능한 오브젝트와 링크된 실행 파일은 역할과 형식 정보가 다르다.

## 9. 필수 실습

### 한 번에 빌드하고 두 종류의 결과 확인하기

- **목적:** 빌드, 프로그램 출력, 종료 상태를 독립적으로 관찰한다.
- **해야 할 일:** 실습 디렉터리에 예제를 직접 입력한다. 기본 명령 `gcc hello.c -o hello`로 빌드하고 상태를 즉시 기록한다. 성공했다면 실행하여 출력과 실행 상태를 기록한다. 이어 경고 옵션을 포함해 빌드한다. 출력 문자열을 자신의 짧은 인사로 바꾸고 `&&` 명령으로 다시 빌드·실행한다.
- **사용할 개념:** GCC 드라이버, `-o`, 상대 경로 실행, 표준 출력, 셸 종료 상태, 재빌드.
- **예상 관찰 결과:** 정상 빌드는 보통 아무 텍스트도 출력하지 않고 상태 0을 남긴다. 정상 실행은 문자열 한 줄과 상태 0을 남긴다. 수정 내용은 재빌드 이후 실행에서 반영된다. 이는 **[GCC/Linux 구현]** 관찰이다.
- **확인 포인트:** 기록에 빌드 명령과 실행 명령이 분리되어 있는가? 변경한 소스와 실행 결과가 대응하는가? `$?`를 언제 읽었는가?

명령 및 기록 안내: [실습 README](../../exercises/00-compilation/0-7/README.md).

## 10. 추가 실습

- ★ **단계별 결과 비교:** 4절 명령으로 `hello-staged`를 만든다. `hello`와 출력 및 종료 상태가 같은지 비교한다. 실행 파일의 바이트 단위 동일성은 요구하지 않는다.
- ★★ **이전 실행 파일 함정 설명:** 정상 빌드 후 소스 복사본에서 세미콜론을 하나 지워 별도 출력 이름으로 빌드를 시도한다. 빌드 실패와 관계없이 기존 정상 실행 파일이 여전히 존재할 수 있음을 기록한다. 실패한 산출물은 실행하지 않는다.

## 11. 확인 문제

1. `-o hello`와 `./hello`의 역할은 어떻게 다른가?
2. 기본 빌드 뒤 `.i`가 없으면 전처리를 생략한 것인가?
3. GCC가 상태 0으로 끝났으면 프로그램의 계산이나 출력도 올바른가?
4. `./hello` 뒤 `ls`를 실행하고 `$?`를 읽으면 누구의 상태인가?
5. ELF와 동적 로더는 C 언어가 의무화한 요소인가?

<details>
<summary>정답과 해설</summary>

1. `-o`는 빌드 출력 이름을 정하는 GCC 옵션이고, `./hello`는 셸에서 실행을 요청하는 경로다.
2. 아니다. 중간 결과를 영구 파일로 남기는 것은 필수가 아니다.
3. 아니다. 번역·링크 성공과 요구 사항 충족은 서로 다른 검사다.
4. 직전 명령인 `ls`의 상태다.
5. 아니다. 이 자료의 Linux 구현 관찰이며 C 표준의 요구 사항이 아니다.

</details>

## 12. 핵심 정리

`gcc hello.c -o hello`는 빌드하고 `./hello`는 실행한다. 출력 내용과 종료 상태를 따로 확인한다. 중간 파일, ELF, 셸 명령은 구현 관찰이고, C의 번역 단계와 표준 함수 의미는 언어 규정이다. 성공한 빌드만 실행에 연결한다.
