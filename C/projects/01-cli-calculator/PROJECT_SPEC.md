# Project Specification

## 프로젝트 목적

사용자 입력을 받아 사칙연산을 수행하고, 정상 입력·잘못된 입력·EOF·연산 오류·종료 요청을 구분하는 CLI Calculator를 직접 설계하고 구현한다. 목표는 정답 코드를 복제하는 것이 아니라 contract를 세우고 C17 규칙 안에서 각 경로를 검증하는 것이다.

## 사용자 관점 동작

- 프로그램을 시작하면 사용 가능한 연산과 종료 방법을 알 수 있다.
- 사용자는 연산과 필요한 피연산자를 입력할 수 있다.
- 유효한 요청에는 계산 결과가 제공된다.
- 잘못된 요청에는 결과로 오해할 수 없는 오류 behavior가 제공된다.
- 한 요청이 끝난 뒤 사용자는 다음 계산을 계속하거나 종료할 수 있다.
- EOF가 발생하면 프로그램은 정의된 방식으로 안전하게 종료된다.

화면 문구, 메뉴 번호, prompt 순서와 같은 표현 세부사항은 구현 전에 학습자가 정한다. 테스트는 문구 자체보다 observable behavior를 기준으로 한다.

## 필수 기능

- 덧셈, 뺄셈, 곱셈, 나눗셈을 지원한다.
- 연산 선택과 피연산자 입력의 성공 여부를 판별한다.
- 입력 함수의 성공, 변환 실패, EOF를 구분한다.
- 지원하지 않는 연산 요청을 거부한다.
- 0으로 나누는 요청을 계산하지 않고 오류로 처리한다.
- 한 번의 계산 뒤 다시 계산할 수 있다.
- 명시적 종료 요청과 EOF 종료를 지원한다.
- 정상·오류·종료 경로를 서로 구분해 검증할 수 있다.

## 선택 기능

필수 기능을 모두 완료한 뒤에만 추가 연산, 계산 기록, 도움말 같은 확장을 고려한다. 선택 기능은 기존 contract와 test를 깨지 않아야 하며, 선택하지 않아도 Project 1 완료에 영향을 주지 않는다.

## 입력 contract

- 구현 전에 지원할 숫자 범위와 표현 방식을 문서에 기록한다.
- 연산 선택과 각 피연산자가 어떤 입력으로 인정되는지 정의한다.
- 입력 성공 여부를 확인한 뒤에만 읽은 값을 사용한다.
- 변환에 실패한 입력이 이후 입력 처리에 어떤 영향을 주는지 정의한다.
- EOF가 연산 선택 중 또는 피연산자 입력 중 발생할 때의 behavior를 정의한다.
- 한 요청의 잘못된 입력이 다음 요청의 값으로 재사용되지 않아야 한다.

입력 API와 parsing 구조는 정답으로 고정하지 않는다.

- `scanf` 계열은 변환 개수를 바로 확인할 수 있지만, 변환되지 않은 입력의 후속 처리를 별도로 설계해야 한다.
- line 기반 입력은 한 요청의 경계를 다루기 쉽지만, 문자열을 숫자로 변환하고 변환 결과를 검사하는 설계가 추가로 필요하다.

학습자는 이 trade-off를 검토하고 자신의 선택과 이유를 `DEVLOG.md`에 기록한다.

## 출력 contract

- 정상 계산에서는 선택한 숫자 표현과 연산 규칙에 맞는 결과를 보여 준다.
- 오류에서는 정상 결과와 혼동되지 않는 정보를 제공한다.
- 사용자가 다음 행동 또는 종료 방법을 이해할 수 있어야 한다.
- exact 문구, 공백, 메뉴 번호는 학습자가 정하되 한 session 안에서 일관성을 유지한다.

## 종료 contract

- 사용자가 정의된 종료 요청을 입력하면 정상 종료한다.
- 입력 stream에서 EOF를 만나면 무한 반복하거나 이전 값을 재사용하지 않고 종료한다.
- 종료 경로에서는 추가 피연산자나 연산을 요구하지 않는다.
- 정상 종료 status를 사용할지, 구분된 종료 status가 필요한지는 설계 이유와 함께 결정한다.

## 오류 처리 요구사항

- 숫자로 해석할 수 없는 입력을 정상 계산으로 처리하지 않는다.
- 지원하지 않는 연산을 실행하지 않는다.
- 0으로 나누기를 평가하지 않는다.
- 필요한 입력이 일부만 제공된 상태에서 결과를 출력하지 않는다.
- 오류 후 계속 실행한다면 다음 요청은 깨끗한 상태에서 시작해야 한다.
- 선택한 숫자 표현에서 발생할 수 있는 범위 문제를 식별하고, 정의되지 않은 동작에 의존하지 않는 정책을 세운다.
- 오류 상태의 표현 방법은 학습자가 정하되 caller와 사용자에게 모호하지 않아야 한다.

## 지원해야 할 연산

| 연산 | 필수 behavior |
|---|---|
| 덧셈 | 유효한 두 피연산자에 대한 합을 제공한다. |
| 뺄셈 | 피연산자 순서가 결과에 반영된다. |
| 곱셈 | 유효한 두 피연산자에 대한 곱을 제공한다. |
| 나눗셈 | 피연산자 순서와 선택한 숫자 표현의 나눗셈 규칙을 따른다. 0인 divisor는 거부한다. |

연산을 어떤 함수 구조로 배치할지, 연산과 입출력을 얼마나 분리할지는 학습자가 결정한다.

## 설계 결정으로 남겨 둘 영역

다음은 구현 전에 학습자가 직접 결정하고 이유를 기록한다.

- 함수 이름과 함수 개수
- parameter type과 return type
- `main`의 책임과 구조
- `scanf` 또는 `fgets` 등 입력 방식
- 입력 parsing과 남은 입력 처리 방식
- `switch` 또는 다른 control-flow 구성
- 메뉴 표현과 연산 선택 표현
- 계산 결과의 자료형과 출력 방식
- 오류 status와 사용자 메시지의 관계
- 한 source 파일 또는 여러 translation unit 구성

선택지는 contract를 만족하는지, 오류를 명확히 구분하는지, 테스트하기 쉬운지를 기준으로 비교한다.

## C17 요구사항

- C17 mode에서 동작하는 표준 C를 사용한다.
- baseline `gcc -std=c17 -Wall -Wextra -Wpedantic -Werror` build가 성공해야 한다.
- compiler warning을 cast나 option 제거로 숨기지 않는다.
- 초기화되지 않은 값, 잘못된 format/argument 대응, 0으로 나누기, signed overflow 등 Undefined Behavior에 의존하지 않는다.
- 입력 함수의 반환값을 사용 전에 확인한다.
- 구현 의존적인 동작이 필요하다면 가정을 명시하고 현재 project 범위에서 필요한지 다시 검토한다.

## AI mentor 규칙

AI는 reviewer / mentor / project specification designer이며 기본 구현자가 아니다. 사용자가 문제 상황, compiler message, 자신의 가설, 시도한 방법을 기록한 뒤에만 단계별 hint를 요청한다.

1. Hint 1: 관련 개념과 확인 지점
2. Hint 2: 구조적 방향
3. Hint 3: project 답안과 분리된 작은 독립 예제
4. Full solution: 마지막 수단

Milestone review에서 AI는 파일을 직접 수정하지 않고 위치, 심각도, 문제, 이유, Hint 1을 먼저 제공한다.

## 금지사항

- 요구사항 문서에 완성 계산기 source나 함수 전체 구현을 넣지 않는다.
- AI가 solution file 또는 답안용 source를 먼저 생성하지 않는다.
- 입력 실패를 무시하고 이전 값이나 초기화되지 않은 값을 사용하지 않는다.
- 0으로 나누기나 선택한 자료형의 Undefined Behavior를 실행하지 않는다.
- warning을 없애기 위해 필수 warning option을 제거하지 않는다.
- 검증되지 않은 선택 기능을 필수 기능과 한꺼번에 확장하지 않는다.

## 완료 기준

- P1-1~P1-8의 요구사항이 구현과 검증 기록에 대응한다.
- 네 필수 연산의 정상 경로가 동작한다.
- 잘못된 숫자 입력, invalid operator, EOF, 0으로 나누기 behavior가 명확하다.
- 명시적 종료와 반복 계산이 정의한 contract대로 동작한다.
- 정상·오류·종료 경로가 서로 오염되지 않는다.
- baseline build가 warning 없이 성공한다.
- 필수 test와 milestone별 직접 추가 test가 통과한다.
- 주요 설계 결정과 디버깅 과정이 `DEVLOG.md`에 기록되어 있다.
