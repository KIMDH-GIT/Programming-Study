# Project Specification

## 프로젝트 목적

공개 계약을 가진 linked list library를 C17로 직접 구현한다. 호출자가 node의 소유권과 수명을 예측할 수 있고, 정상·경계·할당 실패 상황에도 유효한 list를 유지해야 한다.

## Library 동작

- 동적으로 생성한 node를 list에 연결하고 탐색·출력·삭제·전체 정리한다.
- 첫 node를 바꾸는 동작은 pointer-to-pointer를 통해 호출자의 head에 반영한다.
- 공개 header로 계약을 제공하고 library source와 사용 예제를 분리한다.
- 별도 client 예제가 내부 구현을 포함하거나 내부 상태에 의존하지 않고 공개 API만 사용한다.

## 필수 기능

- create와 insert: 성공 시 새 node를 list에 도달 가능하게 연결하고, 실패 시 기존 연결을 보존한다.
- search: 없는 값과 찾은 값을 구분하며 list 상태를 바꾸지 않는다.
- print: 정한 순서·형식에 따라 현재 원소를 관찰하게 하며 list 상태를 바꾸지 않는다.
- delete: 대상이 있을 때 올바른 연결을 유지하며 대상 node의 소유권을 정리한다.
- destroy: 도달 가능한 모든 소유 node를 해제하고 호출자의 head를 빈 상태로 갱신한다.
- 빈 list, 단일 node, 연속 삭제, allocation 실패를 정의된 계약에 맞게 처리한다.

## 선택 기능

중복 정책 확장, tail 관리, 저장된 크기, 사용자 정의 출력, 삽입 위치 추가 등은 필수 기능이 끝난 뒤 고려한다. 선택하지 않아도 완료에 영향을 주지 않으며, 추가한다면 공개 계약과 테스트를 함께 갱신한다.

## 입력 contract

CLI 입력 형식이 아니라 **API precondition과 argument 계약**을 정의한다.

- 각 공개 동작의 유효한 list 상태, 변경 가능한 head의 전달 방법, 검색·삽입·삭제 대상의 유효 범위를 학습자가 명시한다.
- `NULL` head 값(빈 list)과 유효하지 않은 head 저장 위치를 구별하고, 후자의 처리 범위를 계약에 적는다.
- 중복 값의 삽입·검색·삭제 정책, 찾은 결과의 소유권·유효 기간을 명시한다.
- 출력 대상이 필요한 경우 유효한 대상의 조건을 정의한다. client가 내부 node를 직접 조작하도록 요구하지 않는다.
- destroy 뒤 head가 빈 상태일 때 재사용을 허용할지, 별도 초기화가 필요한지 공개 계약으로 정하고 시험한다.

## 출력 contract

- search는 찾음과 찾지 못함을 호출자가 구분할 수 있어야 한다. 반환값인지 출력 매개변수인지는 결정하지 않는다.
- print는 빈 list에서도 정의된 관찰 결과를 제공한다. 문구·구분자·대상 stream 등 구체 표현은 학습자가 정하되 일관되게 유지한다.
- 성공·실패 결과는 정상 데이터와 모호하지 않게 구분한다. 호출자가 소유한 기존 값이 실패 때문에 바뀌지 않는지 명시한다.

## 오류 contract

- 할당 실패를 성공으로 보고하지 않고, 이전에 도달 가능했던 node와 연결을 잃지 않는다.
- 없는 대상의 삭제·검색, 빈 list의 조작, 무효 인자의 처리 방침을 각 API에 명시한다. 계약 밖 인자에 대한 임의의 복구 동작을 요구하지 않는다.
- 실패한 생성·삽입에서 할당된 임시 자원은 누수 없이 정리한다.
- 오류를 status, 반환값, 출력 매개변수 중 어떻게 표현할지 정하되 정상 결과와 충돌하지 않아야 한다.

## 상태와 불변식

- 빈 list의 head는 `NULL`이고, 유효한 list의 각 node는 head에서 연결을 따라 도달 가능하며 끝은 `NULL`이다.
- 연결이 순환하거나 같은 node가 중복 소유되지 않는다. 삽입·삭제 전후 남은 node의 순서와 연결은 정한 정책을 지킨다.
- library가 소유하는 각 동적 node는 정해진 시점에 한 번만 해제한다. 해제된 node를 읽거나 재사용하지 않는다.
- head를 제거하거나 destroy하면 호출자에게 보이는 head도 갱신한다. 새 node를 연결하기 전에 기존 도달 가능성을 잃지 않는다.
- 저장된 size 또는 tail을 선택한다면 실제 연결과 항상 일치해야 한다.

## 설계 결정과 trade-off

- List wrapper는 추가 상태를 묶기 쉽지만 표현과 ownership 계약이 늘어난다. head만 전달하면 상태가 단순하지만 갱신 전달을 명확히 해야 한다.
- tail은 끝 삽입에 유리할 수 있지만 마지막 node 삭제와 실패 시 갱신할 불변식이 늘어난다. 저장된 size도 조회와 갱신 비용을 비교한다.
- 내부 node 표현 공개 여부, 필수 연결 이외의 데이터 필드, 함수 이름·개수·정확한 시그니처·source 파일 개수는 고정하지 않는다. 단, header/source/example 분리는 지킨다.
- 중복 값 정책과 삭제 대상 선택, 반환 status 또는 출력 매개변수는 client의 관찰 가능성과 테스트 용이성을 비교한다.
- 할당 실패를 재현할 seam을 어떻게 둘지 설계한다. 테스트를 위해 공개 API 계약을 불필요하게 복잡하게 만들지 않는다.
- 각 선택과 근거, post-destroy 재사용 정책을 `DEVLOG.md`에 적는다.

## C17 요구사항

- `gcc -std=c17 -Wall -Wextra -Wpedantic -Werror` baseline에서 library와 client를 함께 warning 없이 빌드한다.
- lifetime이 끝난 node 접근, 이중 해제, dangling pointer 역참조, `NULL` 역참조, 유실된 할당을 허용하지 않는다.
- sanitizer 검사만으로 정확성을 단정하지 않고 link 불변식과 정상·실패 경로를 별도로 검증한다.

## 금지사항

- 문서에 완성 C 함수나 답안용 source를 넣지 않는다.
- AI가 먼저 구현 파일을 작성하거나 사용자의 파일을 수정하지 않는다.
- header에 내부 구현을 복제하거나 예제에서 source 파일을 직접 포함하지 않는다.
- 할당 실패나 없는 대상을 정상 성공으로 위장하지 않는다.
- warning option을 제거하거나 sanitizer 오류를 무시해 완료로 처리하지 않는다.

## 완료 기준

- 공개 API·ownership·오류·재사용 정책을 client가 이해할 수 있게 문서화한다.
- 모든 필수 동작과 경계·할당 실패 테스트가 계약을 만족한다.
- 별도 사용 예제가 공개 header와 library source를 함께 빌드하여 동작한다.
- strict C17 build와 ASan을 적용한 최종 실행에서 확인 가능한 누수·메모리 오류가 없다.
- milestone별 직접 추가한 테스트와 설계·검증 기록이 남아 있다.
