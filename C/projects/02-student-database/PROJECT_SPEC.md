# Project Specification

## 프로젝트 목적

학생 데이터를 동적 배열에 담아 관리하고 파일에 저장·복원하는 Student Database를 직접 설계하고 구현한다. 목표는 정답 코드를 복제하는 것이 아니라 사용자 behavior와 데이터·파일·모듈 contract를 정의하고 C17 규칙 안에서 검증하는 것이다.

## 사용자 관점 동작

- 사용자는 학생을 추가·삭제·검색하고 목록과 정렬 결과를 확인할 수 있다.
- 중복 ID와 존재하지 않는 학생 등 실패 요청은 정상 결과와 구분된다.
- 저장한 데이터는 프로그램을 종료하고 다시 시작한 뒤에도 복원된다.
- 파일에 접근할 수 없거나 파일 내용이 유효하지 않을 때 정의된 오류 behavior를 보인다.
- 종료하면 열린 파일과 동적 자원이 정리된다.

화면 문구, 메뉴 번호, 학생의 정확한 필드, 검색 기준과 정렬 기준은 학습자가 정한다. 테스트는 문구 자체보다 observable behavior를 기준으로 한다.

## 필수 기능

- 유효한 학생 데이터와 고유 ID의 의미를 정한다.
- `main`, student, file 모듈의 책임과 공개 interface를 정의하고 여러 translation unit으로 구성한다.
- 학생 레코드를 동적 배열에 보관하며 크기·용량·할당 실패를 관리한다.
- Add에서 중복 ID를 검사하고 정한 거부 또는 갱신 정책을 일관되게 적용한다.
- Delete와 Search에서 대상이 있는 경우와 없는 경우를 구분한다.
- List에서 빈 DB와 여러 레코드를 구분해 보여 준다.
- Sort에서 학습자가 선택한 정렬 기준을 일관되게 적용한다.
- 저장 파일 형식을 명시하고 Save와 Load를 구현한다.
- 시작 시 복원하고 종료 시 소유한 동적 자원과 파일을 정리한다.
- 재실행 후 데이터 유지, 파일 오류, 여러 파일 build를 검증한다.

## 선택 기능

필수 기능을 마친 뒤에만 추가 검색 조건, 추가 정렬 기준, 통계 등을 고려한다. 선택 기능은 필수 contract와 테스트를 깨지 않아야 하며, 선택하지 않아도 Project 2 완료에 영향을 주지 않는다.

## 입력 contract

- 학생별 필수 입력, 허용 범위와 길이, 유효한 ID의 조건을 구현 전에 정한다.
- 명령 선택, 학생 입력, 검색·삭제 대상 입력의 성공과 실패를 구분한다.
- 잘못되거나 불완전한 입력을 유효한 레코드나 다음 명령으로 오해하지 않는다.
- 입력 오류 후 계속할지 종료할지 정하고 이후 상태가 오염되지 않게 한다.
- 입력 API와 parsing 방식은 정답으로 고정하지 않는다. 필드 단위 입력은 간단할 수 있지만 남은 입력 처리에 주의가 필요하고, 줄 단위 입력은 경계를 다루기 쉽지만 변환 검증이 필요하다.

## 출력 contract

- 각 명령의 성공·실패와 다음 행동을 사용자가 구분할 수 있다.
- Search는 찾음·찾지 못함을, List는 비어 있음·레코드 있음 상태를 구분한다.
- Sort 결과는 선택한 순서와 일치하며 동일한 기준값의 처리 방식을 정한다.
- 저장·복원 실패를 성공으로 표시하지 않는다.
- exact 문구, 출력 순서와 메뉴 번호는 학습자가 정하되 일관성을 유지한다.

## 오류 및 파일 contract

- 중복 ID의 처리 정책을 정하고 Add가 적용한 결과를 사용자에게 알린다.
- 없는 대상에 대한 Delete·Search는 다른 레코드를 변경하지 않는다.
- 메모리 할당 실패와 파일 열기·읽기·쓰기·닫기 실패의 영향을 정의한다.
- 파일이 없는 첫 실행과 접근 실패, 손상되거나 불완전한 내용은 구분해 처리한다.
- Load 실패 또는 부분 읽기 뒤 메모리에 남길 상태를 정하고 테스트한다.
- Save 실패를 성공처럼 보고하거나 기존 유효 데이터를 묵시적으로 잃지 않게 정책을 정한다.
- 저장 시점과 종료 시 저장 여부를 명시해 재실행 기대값을 결정한다.

## 상태와 불변식

- 유효한 학생 레코드만 현재 크기 안에 있고, 크기는 할당된 용량을 넘지 않는다.
- 적용한 중복 ID 정책에 따라 현재 DB에 서로 충돌하는 ID가 남지 않는다.
- Add·Delete 실패가 다른 레코드와 배열의 유효 상태를 깨지 않는다.
- Search·List는 조회만 수행하며 Sort는 레코드를 잃거나 복제하지 않는다.
- 배열을 다시 할당할 때 기존 포인터와 내부 별칭의 유효성을 검토한다.
- 배열·레코드·파일의 소유자와 해제 시점을 정하고 이중 해제·누수를 피한다.
- Save·Load 전후에 문서화한 필드와 레코드의 의미가 유지된다.

## 저장 형식 설계

필드와 레코드의 경계, 숫자·문자의 표현, 빈 DB, 버전 또는 호환성 필요 여부를 학습자가 정해 명시한다. text 형식은 사람이 읽기 쉽지만 분리 문자와 parsing 검증이 필요하다. binary 형식은 읽고 쓰기 쉬워 보일 수 있지만 구조체를 통째로 저장하면 padding, pointer, 표현 방식 때문에 호환성을 보장할 수 없다. 구체적인 파일 형식과 경로는 여기서 고정하지 않는다.

## 사용자 설계 결정으로 남겨 둘 영역

- Student 멤버와 각 필드의 유효 범위, 최대 학생 수를 둘지 여부
- 동적 배열의 용량 증가 정책과 할당 실패 시 상태 보존
- 중복 ID의 거부 또는 갱신 정책과 사용자에게 보이는 결과
- 검색 키와 정렬 기준, 동률 처리
- 함수 이름, parameter/return type, 오류 encoding과 모듈 공개 API
- 메뉴 번호, 입력 방법, 저장 시점과 파일 경로·형식의 세부 내용

각 선택은 데이터 보존, 오류 구분, 테스트 가능성의 관점에서 비교하고 이유를 `DEVLOG.md`에 기록한다.

## C17 요구사항

- C17 mode에서 동작하는 표준 C를 사용한다.
- 모든 translation unit을 포함한 baseline `gcc -std=c17 -Wall -Wextra -Wpedantic -Werror` build가 성공해야 한다.
- warning을 cast나 option 제거로 숨기지 않는다.
- 할당 크기 overflow, 범위 밖 접근, 초기화되지 않은 값, 해제 후 사용, 이중 해제 등 Undefined Behavior에 의존하지 않는다.
- 입력·파일 함수의 반환 결과와 소유권·lifetime을 사용 전후에 검토한다.
- 선언과 정의를 분리하고 header의 중복 정의와 누락된 link 대상을 피한다.

## 금지사항

- 완성 source, 함수 전체 구현이나 답안용 파일을 명세에 넣지 않는다.
- 동적 배열을 고정 크기 배열로 대신해 필수 요구사항을 생략하지 않는다.
- 실패한 입력·할당·파일 작업을 성공으로 간주하지 않는다.
- 구조체의 메모리 배치를 검토 없이 영속 파일 형식으로 가정하지 않는다.
- warning을 없애기 위해 필수 warning option을 제거하지 않는다.
- 선택 기능을 필수 기능 검증 전에 한꺼번에 확장하지 않는다.

## 완료 기준

- P2-1~P2-12의 요구사항이 구현과 검증 기록에 대응한다.
- 빈 DB·단일·여러 레코드에서 Add·Delete·Search·List·Sort가 정의한 정책대로 동작한다.
- 명시한 형식으로 Save·Load가 동작하고 시작 시 복원·종료 시 정리한다.
- 재실행, 파일 오류, 잘못된 입력, 할당·소유권 경계가 검증된다.
- 여러 파일을 함께 baseline으로 build할 때 error와 warning이 없다.
- 필수 test와 milestone별 직접 추가 test가 통과하고 주요 선택과 디버깅이 `DEVLOG.md`에 기록되어 있다.
