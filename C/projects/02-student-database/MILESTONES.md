# Milestones

각 milestone은 몇 시간에서 하루 안에 완료할 수 있는 범위로 나누었다. 코드를 작성하기 전에 사용자 관점 contract와 설계 결정을 기록하고, 완료 조건을 검증한 뒤 다음 단계로 넘어간다.

## Milestone 1 — 데이터 규격과 모듈 경계

### 목표

학생 데이터와 명령의 observable behavior를 정하고 `main`, student, file 모듈 사이의 책임과 interface를 설계한다.

### 관련 curriculum Step

- P2-1. 학생 데이터와 기능 규격
- P2-2. `main`, student, file 모듈 interface

### 관련 기존 Part

- Part 5, 10: 입력·출력과 함수 contract
- Part 19: 학생 구조체와 기능
- Part 24~25: source·header와 공개 interface

### 필수 behavior

- 유효한 학생과 고유 ID의 조건, Add·Delete·Search·List·Sort의 성공·실패를 정의한다.
- 사용자 입력·처리·파일 저장의 책임과 모듈 간 데이터 전달을 구분한다.
- 빈 DB와 명시적 종료가 사용자에게 어떻게 보이는지 정한다.

### 완료 조건

- 데이터·입력·출력·오류 contract가 문서화되어 있다.
- 각 모듈이 소유하는 상태와 공개할 동작이 설명되어 있다.
- 설계 이유와 미결정 사항이 `DEVLOG.md`에 기록되어 있다.

### 검증해야 할 동작

- 빈 DB의 조회·목록·종료가 서로 다른 상태로 식별된다.
- 정의한 학생 입력 범위와 중복 ID 정책이 모순되지 않는다.

### 사용자가 직접 결정할 설계 사항

- Student의 멤버, 입력 범위, 검색 키, 메뉴 번호와 종료 방식
- 모듈별 interface, 함수 이름, parameter/return type과 오류 표현

### 사용자가 직접 생각할 질문

- 사용자 요청 한 건은 어디서 시작하고 끝나는가?
- 모듈 간 데이터 소유권을 어떻게 설명할 수 있는가?

## Milestone 2 — 동적 배열과 Add

### 목표

학생 수에 따라 관리되는 동적 배열을 준비하고 유효한 학생의 추가와 중복 ID 정책을 검증한다.

### 관련 curriculum Step

- P2-3. 동적 학생 배열
- P2-4. Add와 중복 ID 검사

### 관련 기존 Part

- Part 11, 14~16: 배열 경계와 포인터 전달
- Part 18: 동적 배열, 할당 실패, ownership
- Part 19: 구조체 배열과 학생 등록

### 필수 behavior

- 빈 상태에서 한 명·여러 명을 추가하고 필요하면 저장 공간을 확장한다.
- 중복 ID 입력에 정한 정책을 적용하고 사용자에게 결과를 구분해 보여 준다.
- 잘못된 입력이나 할당 실패 뒤 유효한 레코드와 배열 상태를 보존한다.

### 완료 조건

- 현재 크기와 용량의 관계가 항상 유효하다.
- 단일·복수 추가와 중복 ID 경로의 결과를 확인했다.
- 용량과 할당 실패에 대한 선택과 근거를 기록했다.

### 검증해야 할 동작

- 빈 배열에 첫 레코드를 추가할 수 있다.
- 여러 건 추가 뒤 기존 레코드가 유지된다.
- 중복·유효하지 않은 입력이 정책 밖의 레코드를 만들지 않는다.

### 사용자가 직접 결정할 설계 사항

- 초기 용량과 증가 정책, 최대 건수 여부
- 중복 ID의 거부 또는 갱신 정책과 할당 실패 표현

### 사용자가 직접 생각할 질문

- 확장 실패 시 어느 상태가 그대로 남아야 하는가?
- 배열이 이동하면 이전 원소 주소를 가리키던 포인터는 어떻게 되는가?

## Milestone 3 — Delete와 Search

### 목표

있는 학생과 없는 학생을 구분해 삭제·검색하며 상태 변경 뒤에도 레코드의 의미를 유지한다.

### 관련 curriculum Step

- P2-5. Delete
- P2-6. Search

### 관련 기존 Part

- Part 11, 15: 배열 순회와 경계
- Part 16, 18: 포인터와 동적 객체 lifetime
- Part 19: 학생 삭제·검색

### 필수 behavior

- 있는 대상의 삭제는 해당 학생만 제거하고, 없는 대상은 다른 데이터를 변경하지 않는다.
- Search는 찾음·찾지 못함을 구분하고 조회만 수행한다.
- 첫·중간·마지막 학생 삭제 뒤 크기와 나머지 레코드가 일관된다.

### 완료 조건

- 빈 DB·단일·복수 레코드에서 삭제와 검색 결과가 정의한 contract와 일치한다.
- 삭제 뒤 다른 학생의 검색 결과가 유지된다.
- 상태 변경과 참조 lifetime에 대한 선택을 기록했다.

### 검증해야 할 동작

- 없는 학생의 삭제·검색은 정상 성공으로 표시되지 않는다.
- 삭제한 학생은 검색되지 않고 남은 학생은 검색된다.
- 마지막 학생 삭제 뒤 빈 상태로 돌아간다.

### 사용자가 직접 결정할 설계 사항

- 검색 키와 일치 판정, 삭제 뒤 레코드 배치 방식
- 조회 결과의 표현, 무효화되는 참조의 수명

### 사용자가 직접 생각할 질문

- 삭제 전후의 어떤 포인터나 index를 더 이상 믿을 수 없는가?
- 찾지 못함과 잘못된 입력을 같은 결과로 다뤄도 되는가?

## Milestone 4 — List와 Sort

### 목표

빈 상태와 여러 레코드의 목록을 보여 주고 선택한 정렬 순서로 일관되게 정렬한다.

### 관련 curriculum Step

- P2-7. List
- P2-8. Sort

### 관련 기존 Part

- Part 9, 11: 순회와 배열 경계
- Part 18: 동적 배열 정렬
- Part 19: 학생 목록·정렬

### 필수 behavior

- List는 빈 DB를 식별하고, 있는 레코드를 빠짐없이 보여 준다.
- Sort는 선택한 기준과 동률 정책에 맞춰 레코드를 정렬한다.
- 정렬 뒤 레코드 수, 고유 ID, 각 학생의 데이터가 보존된다.

### 완료 조건

- 빈·한 명·여러 명 목록과 정렬을 검증했다.
- 정렬 기준과 동률 정책을 문서화했다.
- 추가·삭제 뒤 목록과 정렬 결과가 상태와 일치한다.

### 검증해야 할 동작

- 빈 DB와 한 명의 정렬에서 범위 밖 접근이 없다.
- 역순 또는 순서가 섞인 데이터가 정해진 순서로 나온다.
- 정렬 전후 검색 가능한 학생의 집합이 같다.

### 사용자가 직접 결정할 설계 사항

- 정렬 기준, 오름차순·내림차순, 동률 순서
- List의 표시 필드와 정렬 후 원본 순서에 대한 정책

### 사용자가 직접 생각할 질문

- 같은 정렬 키를 가진 학생들의 결과는 어떻게 예측할 수 있는가?
- 정렬이 데이터 내용 자체를 바꾸지 않았음을 어떻게 확인할 수 있는가?

## Milestone 5 — 저장 형식과 Save·Load

### 목표

메모리의 학생 데이터를 명시한 형식으로 파일에 저장하고 읽어 다시 사용할 수 있게 한다.

### 관련 curriculum Step

- P2-9. 저장 파일 형식
- P2-10. Save와 Load

### 관련 기존 Part

- Part 13: 문자열과 길이 경계
- Part 18: 읽은 레코드의 동적 저장
- Part 23: 파일 형식, 열기·읽기·쓰기·닫기와 오류

### 필수 behavior

- 레코드·필드 경계와 빈 DB 표현을 명시한다.
- Save 후 Load에서 정한 필드와 학생 수가 보존된다.
- 유효하지 않거나 불완전한 파일과 읽기·쓰기 실패를 구분해 처리한다.

### 완료 조건

- 저장 형식과 파싱 가능한 범위를 문서화했다.
- 빈·단일·복수 레코드의 Save·Load 결과가 contract와 일치한다.
- 실패한 Load 뒤의 메모리 상태와 Save 오류 결과가 정의되어 있다.

### 검증해야 할 동작

- 저장한 데이터를 다시 읽으면 레코드의 의미가 같다.
- 손상된 파일이 부분적으로 유효한 DB로 묵시적으로 받아들여지지 않는다.
- 파일 접근 실패를 성공으로 표시하지 않는다.

### 사용자가 직접 결정할 설계 사항

- 파일 경로·형식·필드 표현과 구분 방식
- Save 시점, 실패 시 기존 파일과 메모리 상태를 다루는 정책

### 사용자가 직접 생각할 질문

- 구조체 메모리를 그대로 저장하면 어떤 정보가 파일 형식에 섞이는가?
- Load가 중간에 실패하면 기존 DB와 새로 읽은 데이터는 어떻게 되는가?

## Milestone 6 — 시작·종료와 최종 검증

### 목표

시작 시 복원·종료 시 정리를 통합하고 재실행·파일 오류·다중 파일 build를 최종 확인한다.

### 관련 curriculum Step

- P2-11. 시작 시 복원과 종료 시 정리
- P2-12. 재실행·파일 오류·다중 파일 build 최종 검증

### 관련 기존 Part

- Part 0: compile, link와 실행
- Part 18: 해제·소유권과 object lifetime
- Part 23: 파일 오류와 재실행 후 복원
- Part 24~25: 다중 파일 link와 header guard

### 필수 behavior

- 시작 시 저장 파일을 복원하고 첫 실행의 파일 없음과 실제 파일 오류를 구분한다.
- 종료 시 정의한 저장 정책을 지키고 동적 메모리·파일을 정리한다.
- 모든 translation unit을 baseline option으로 build하고 정상·오류 경로를 다시 검증한다.

### 완료 조건

- 종료 후 재실행해 저장 데이터가 복원되는 것을 확인했다.
- 파일 열기·읽기·쓰기 오류와 종료 경로의 결과가 contract와 일치한다.
- `gcc -std=c17 -Wall -Wextra -Wpedantic -Werror` 다중 파일 build에 warning과 error가 없다.
- `TEST_PLAN.md`의 필수 테스트와 직접 추가한 테스트가 통과하고 최종 결과를 `DEVLOG.md`에 기록했다.

### 검증해야 할 동작

- 수정·저장·종료·재실행 뒤 DB 상태가 정의한 기대값과 같다.
- 오류 종료에서도 소유한 자원이 정리되고 잘못된 성공 표시가 없다.
- clean build에서 중복 정의·누락된 symbol·warning이 없다.

### 사용자가 직접 결정할 설계 사항

- 시작 시 파일이 없는 경우와 오류가 난 경우의 진행 정책
- 종료 시 저장 여부, 실패 보고 방식과 정리 순서

### 사용자가 직접 생각할 질문

- 파일 오류가 있어도 계속할 때 사용자가 어떤 데이터 상태를 보게 되는가?
- compile 성공과 별개로 어떤 경로에서 누수나 stale data가 생길 수 있는가?
